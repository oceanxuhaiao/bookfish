## P1-1 完读后的计划归档

### 审核指出的问题
`PlanCoordinator` 切下一本时只跳过已完读条目，不归档；归档只发生在 `Library.syncPlan()`（下次打开时）。运行期计划状态与真实阅读状态不一致。

### 根因
交接逻辑分两步：`PlanCoordinator` 只调 `selectPlanned()`，归档留给启动对账。中间窗口里，"已读完"的书仍然留在 `plan.items` 里，`completedCount` 不动，`selection.queue` 还把它当排队项。

### 改法
新增 `Library.completeCurrentPlanned(bookKey, { switch })`，把四件事放进**同一次** `change()`：

```
1. archiveItem(plan, item.id, 'completed', now, 'finished_while_planned')
2. this.invalidate(draft)              // 旧书未完成任务与 review job 失效
3. draft.selected = next.bookKey
4. next.startedAt = now               // 计划开始时间
```

关键设计决定：

- **归档是记账，不看门禁。** 暂停 / 作息 / 休息 / 读后感 pending / 计划关闭时，条目照样归档（计划说的是事实），只是不切换。等到门禁打开，同一次调用补上切换。
- **只有真完读才能触发。** `completeCurrentPlanned` 入口就校验 `this.view(current).complete`，否则抛 `Only a genuinely finished book can end its plan entry`。完读判定本身一行没改。
- **幂等。** 条目已不在 `items` 且没有可切换目标时直接返回，不写盘；重复回调不会二次归档。
- **已完读条目拒绝被改写。** `removeFromPlan` 现在对 complete 的条目抛 `This book is already finished; its plan entry is recorded as completed` —— 完读是唯一必须诚实的一种结局。
- **`selection.queue` 投影过滤已完读条目。** 手工点开 `the book is complete` 的情况也不再把书当 `queued` 卖出去。

### 证据
`tests/plan-archive.test.ts`（8 例）逐条对应审核的 8 项要求：

| 要求 | 用例 |
| --- | --- |
| A 完读自动切 B，A 进 archive | archives A while switching to B, without any restart |
| A、B 都归档 | keeps both archived entries after two hand-offs |
| C 是最后一本也要归档 | archives the last book even though nothing comes next |
| 读后感 pending 不得提前切书 | archives without switching while the finished review is still pending, then hands off |
| 终态失败后按既有规则继续 | 同上用例后半段 |
| 重复回调不重复归档 | does not archive twice for a repeated completion callback |
| 不重启也更新 | 用例 1（无重启，断言 `completedCount === 1`） |
| 重启后一致 | keeps the archive and the order across a restart |

补充：`never projects a finished entry as a queued row`、`refuses to rewrite a finished entry as skipped or removed`。

## P1-2 停止当前书的原子性

### 审核指出的问题
`removeFromPlan()` 分三次写入：先归档、再 `select()`、最后 `updatePlan(markStarted)`。中途崩溃会让计划与选择不一致。

### 根因
三步各自 `change()`，任意两步之间失败都会留下中间态：条目已归档但 `selected` 还指向旧书，或 `selected` 已切换但 `startedAt` 没写。

### 改法
整个 stop 收进**一次** `change()`：

```
archiveItem(draft.plan, id, status, now, reason)
  ↓（仅 stop）
nextReadable(draft, { exclude: 旧书 })      // 跳过已完读、已下架、notBefore 未到
invalidate(draft)                            // 旧书 pending 任务失效
draft.selected = next.bookKey
next.startedAt = now
```

三个额外的硬约束：

1. **没有可读的下一个 → 抛错，什么都不改。** 消息：`No other planned book is readable right now; remove it from the plan while keeping it open, or pause reading`。
   这条是刻意的：审核要求"不得出现当前书已移出计划却仍被当成正常在读书"。只要不允许"没有接续者还移除"，这个状态就**无法被构造出来**。替代路径是 `keepReading: true`（面板上是"移出计划（继续读这本）"）。
2. **暂缓不能被绕过。** `nextReadable` 在 stop 路径上跳过 `notBefore` 未到的条目；如果唯一的候选被暂缓，等同于"没有下一本"，直接拒绝。面板上也把这个按钮藏起来。
3. **原书进度一字不动。** 只归档计划条目，不碰 `frontier`。

### 证据
`tests/plan-stop-atomic.test.ts`（7 例），用注入式 `write` 在提交边界模拟磁盘失败：

| 要求 | 用例 |
| --- | --- |
| 单次提交 | archives, invalidates and switches in a single commit（同时断言旧书 pending 任务已失效） |
| 暂缓不被绕过 | skips a deferred entry and picks the next readable one / refuses the stop when the only other planned book is deferred |
| 故障注入：写入失败 | leaves nothing behind when the commit fails, and the retry then succeeds（条目、选择、进度全部未变） |
| 重启后可继续 | reopens into a state that can continue reading, both after success and after failure |
| 不会出现"选中了但计划没条目" | never reports a switched selection without its plan entry（含 `startedAt` 一致） |
| 非计划驱动的在读书也能停 | stops a book that the plan was not driving, without touching the plan order |

## P1-3 批量导入的磁盘预算

### 审核指出的问题
`BATCH_STAGING_BYTES` 检查的是单个文件而不是整批；100 MiB 限制在暂存之后才检查。

### 根因
预算校验点分散在 `stage()`（且只比 `item.size`）和 `addBatchItems()`（只有数量上限），没有"整批累计"的视角，也没有"写入前拒绝"。

### 改法
统一成三层，全部在写盘前：

| 层 | 位置 | 检查 |
| --- | --- | --- |
| 声明期 | `addBatchItems()` / `ImportBatches.addItems()` | 单文件 ≤ 100 MiB、单批累计 ≤ 1 GiB、条目 ≤ 100；超标进 `tooLarge` / `overBudget` 并回传，不写一个字节 |
| 分片期 | `stage()` | 整批声明量 ≤ 1 GiB、`item.size` ≤ 100 MiB、`offset+len ≤ item.size`，任一不满足即拒绝 |
| 解包期 | `importZip()` | 传入 `{maxEntries, maxTotalBytes, maxEntryBytes}` 给既有 hardened worker；展开后总量 > 1 GiB 或单个 > 100 MiB 直接拒绝 |

`ZIP_MAX_BYTES = 512 MiB` 在 `zipBegin` 与每个 `zipChunk` 都校验。

预算可通过 `ImportBatches` 构造参数注入（`budget: {batchBytes, fileBytes, zipBytes}`），默认值就是出厂值，测试用小额度验证边界而不必真的写 1 GiB。

### 证据
`tests/import-batch-budget.test.ts`（12 例）：

- `pins every ceiling the task book names`：断言常量就是 100 MiB / 100 项 / 1 GiB / 并发 2 / 512 MiB。
- 101 本 → 接受 100、第 101 报 `overflow`、暂存目录里 0 个文件。
- 单本 100 MiB + 1 字节 → `tooLarge`，条目未加入。
- 恰好 100 MiB 通过；恰好 1 GiB（10×100 MiB + 24 MiB）通过；再加 1 字节 → `overBudget`。
- 分片到达时复核：篡改持久化里的 `item.size` 后 `stage()` 拒绝。
- 超 100 MiB 的条目即使分片上传也被拒绝。
- ZIP 展开超预算 / 单条目超限 → 拒绝（注入小额度触发 worker 的 `解压后总大小超过限制`）。
- ZIP 上传体 > 512 MiB → `zipBegin` 拒绝。
- 一个批次失败不影响另一批已成功的书；`forget` + `cleanStale` 只删自己的目录，不碰别的批次，也不删非自己创建的目录。

## P1-4 降级时的计划数据丢失

### 审核指出的问题
v1.0 把 `plan` / `importBatches` 加进 `library.json`，旧版本不认识，再次保存就会抹掉。仅靠文档提醒不够。

### 根因（比审核描述的更麻烦）
`LibraryState.schema` **不落盘**：`bookStorage.hydrate()` 把文件布局 4/5/6/7 一律映射成 state 3。所以只改 state 版本号，旧版本仍然读得开、仍然会静默覆盖。必须改**文件布局**版本。

### 改法
1. 文件布局 `< 6` 保持不变；本轮把写出的文件 `schema` 从 `6/7` 提升到 **`8`**，`writeArchive()` 同样写 8。
2. `bookStorage.hydrate()` 映射：`8 → state 4`，`4/5/6/7 → state 3`，其他原样透传。
3. `validateState()` 接受 state `1..4`，一律产出 4；其他值抛 `Unsupported or invalid library state`。
4. `open()` 把 8 当作 history-backed 布局（与 6/7 同分支），不再触发"legacy 备份"分支。

旧版本读到 8 的完整链路（我在 `tests/schema-downgrade.test.ts` 里逐行复刻了那两条判断）：

```
v0.66.7 hydrate(): [4,5,6,7].includes(8) === false  → schema 仍是 8
v0.66.7 validateState(): schema !== 1/2/3           → throw 'Unsupported or invalid library state'
                                                      → open() 失败，库打不开，不会写入任何东西
```

这是 **fail-closed**：降级后旧版本拒绝打开，而不是打开后静默丢计划。代价是降级期间库不可用——这比丢数据好，且已被审核选项明确允许（"提升持久化 schema 版本，让旧版本拒绝打开新格式"）。

### 证据
`tests/schema-downgrade.test.ts`（7 例）：

- 新版本写出 `schema: 8`，并带上 `plan.items` 顺序与 `importBatches`。
- 旧版本的 gate 对 5/6/7 放行、对 8 拒绝。
- v0.66.7 快照（布局 6、无新字段）能被打开，书与进度完好，计划/批次为空，下次写入变成 8。
- 新版本重读自己的快照，计划顺序、条目 id、`revision` 都不变。
- JSON 导出与 `.bfbak` 归档两条备份路径都保住计划顺序（归档/恢复）。
- 升级提交失败时 `library.json` 字节完全不变（SHA-256 相同），修好后同一份文件能正常升级。

### 附带修正
4 个既有测试断言文件 `schema === 6`，改为 8（`history` / `journal` / `paged-book` / `reviews`）。这是布局契约的变更，不是放宽检查。
