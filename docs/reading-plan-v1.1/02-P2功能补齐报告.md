# 02 · P2 功能补齐报告

四个 P2 都是"后端已有能力、前端没有入口"或"边界条件没守住"，逐个补齐。

---

## P2-1 单本取消与重新选择文件

### 补齐内容

| 操作 | 入口 | 后端方法 |
| --- | --- | --- |
| 取消等待中的单本 | 每行"取消这本" | `import_batch_cancel_item` |
| 取消正在处理的单本 | 同上（`pending/importing/processing/validating` 都显示） | 同上，会 terminate 该条的 worker |
| 取消后其他书继续 | — | 只改本条目，`settleBatch()` 重新收敛批次状态 |
| 取消状态保留 | 行内显示"已取消" + 原因 | `BatchItem.status = 'cancelled'` 持久化 |
| 单本重试 | `failed` / `cancelled` → "重试这本" | `import_batch_retry` |
| 真正重新选择文件 | `needs_reselect` → "重新选择文件" | `import_batch_reselect` + 分片上传 |

### 重新选择的完整链路

```
用户点"重新选择文件"
  → 弹出普通文件对话框（不是自动上传某个猜测的文件）
  → ImportBatches.reselect(batchId, itemId, {size})
       · 条目必须处于 needs_reselect
       · 大小必须与批次记录完全一致，否则拒绝：
         "This entry expects a N byte file; the picked file is M bytes"
       · 删掉旧的残片、状态回到 pending、attempts 归零、批次回到 running
  → 分片上传到同一个 itemId
  → 最后一个分片落盘后 pump()，重新入队
  → 完成后仍是一条记录，itemId 不变，批次顺序不变
```

关键点：**普通 retry 不能代替重新选择**。`retryItem()` 只对 `failed/cancelled` 生效，`needs_reselect` 走 `reselect()`；两条路径在代码里是分开的，UI 上也给了不同按钮。

### 证据
- `tests/webui/batch-import.test.ts`：「cancels one item while the others keep importing」→ 结果状态是 `['cancelled','completed']`。
- 同文件：「lets the user pick the lost file again and finishes the same entry」→ 只上传一半字节 → `needs_reselect` → 面板点"重新选择文件" → 选同长度文件 → 最终 `completed`，且 `items` 仍只有 1 条、`id` 与原来相同。
- `tests/import-batch-chunks.test.ts`：「re-upload after reselect restores the same item instead of creating a new one」→ 同 id、同顺序、大小不符时拒绝、非 `needs_reselect` 时拒绝。

## P2-2 批次恢复界面

### 补齐内容

面板挂载即调用 `import_batch_status()`（无参）拿摘要列表，渲染"导入记录（未完成 N 批）"：

- 未完成（`preview` / `running`）排在最前；
- 显示 `标题 · 状态 · 已完成/总数`；
- `needs_reselect` 的行额外提示"N 本需重新选择文件"；
- `running` 的行提示"继续在后台进行"；
- 点任意一行 → 打开该批次详情（预览 / 进度 / 逐条操作）；
- 已完成/已取消的行有"清理记录" → `import_batch_forget`（只删批次记录，**不删书**）；
- 已完成批次在详情里有"加入阅读计划"。

### 为什么这样做
宿主重启后，`ImportBatches.resume()` 会续跑未完成项并把救不回来的标成 `needs_reselect`；但如果面板不展示历史，用户就失去了对这些任务的操作入口——书可能已经进架，任务却像消失了一样。摘要列表就是这个入口。

### 证据
`tests/webui/batch-import.test.ts`：

- 「offers the way back into an unfinished batch after a remount」：先在后台建批次并上传完整字节，销毁面板重新挂载（等价于宿主重开面板）→ 出现"未完成 1 批"→ 点进去能看到"开始导入"和《待续》。
- 「forgets a finished batch record without touching the books」：清理后 `importBatches` 为空、`books` 仍有 1 本。

## P2-3 单本加入计划与系列管理

### A. 单本加入阅读计划
书籍详情页（`client.ts` 的 `showBook`）新增：

- 未在计划且未读完 → 按钮"加入阅读计划" → `plan_add([bookKey])`；
- 已在计划 → 显示"已在阅读计划第 N 位"（只读标记，不重复入队）；
- 已读完 → 显示"这本书已读完，不能再排进计划"，**不给按钮**。

加入操作只写 `plan.items`，不动 `frontier`，也不改 `selected`（不会因为入队就切书）。

### B. 系列管理
计划页新增（`src/webui/plan.ts`）：

| 能力 | 入口 |
| --- | --- |
| 创建系列 | 行内"系列"下拉 → "新建系列…"（输入名称后 `create` + 立即把该书加入） |
| 加入系列 | 同一处下拉选择已有系列 → `assign` |
| 移出系列 | 下拉选"不分组"，或系列组内"移出本系列" → `assign seriesId: null` |
| 重命名 | 系列组内输入框 + "重命名" |
| 展开/折叠 | 每个系列是 `<details>` |
| 整组移动 | "整组上移 / 整组下移" → `move_series`（组内保序） |
| 组内顺序 | 成员行内"上移 / 下移" → `move`（同样受当前书锁定约束） |
| 解散系列 | "解散分组" → `delete`（只取消分组，顺序与进度不变） |
| 分组建议 | 独立"系列建议"卡片 + "看分组建议" → `plan_suggest` |

**建议永远只是建议**：`plan_suggest` 只返回 `{name, bookKeys, evidence, ambiguous}`；UI 明确写出"自动识别只提供建议，确认后才会建立分组"，`ambiguous` 的建议会额外标注"可能是同一本拆开"。采纳需要点"采用建议"，此时才 `create`。

### 证据
`tests/webui/plan-panel.test.ts`（9 例，本轮 +3）：

- 「creates, renames, ungroups and reorders a series from the plan page」：建组 → 摘要显示"三本一组 · 2" → 改名生效 → 移出一本后 `count` 变 1 → 解散后 `series == []` 且顺序不变。
- 「adopts a grouping proposal only when the user asks for it」：点"看分组建议"后 `series` 仍为空（没有自动成组）；点"采用建议"后才出现分组。
- 「adds a single book to the plan from the book detail page」：书架 → 书籍详情 → "加入阅读计划" → `plan.items` 出现该书。
- 既有 6 例继续通过（顺序、锁定、跳过、停止、整组移动）。

## P2-4 分片上传完整性

### 补齐内容
`ImportBatches.stage()` 改为严格 append-only：

| 情况 | 之前的漏洞 | 现在 |
| --- | --- | --- |
| 跳跃上传（offset > 已写长度） | 允许 `r+` 写到任意偏移，形成稀疏文件 | 拒绝：`Import chunk skipped bytes; upload the missing part first` |
| 不一致重叠（offset < 已写 && 越过边界） | 可覆盖已有字节 | 拒绝：`overlaps the staged data inconsistently` |
| 重复分片（offset < 已写 && 完全在已写区间内） | 静默重写 | **逐字节比较**：一致则幂等接受（`replayed: true`），否则 `replay does not match` |
| 稀疏伪装 | 文件长度可与 `item.size` 一致但内容是洞 | 每次写完校验 `statSync(file).size === offset + len` |
| 最终长度 ≠ 声明大小 | 只在 `launch()` 查一次 | `launch()` 仍查，且不匹配直接 `needs_reselect`，不会带病导入 |
| 上传未完成就导入 | `start()` 可以立刻派发 | 分片只在**最后一片落盘**后 `pump()`；`start()` 派发前再查一次真实长度 |

`zipChunk()` 改成同一套规则（之前只校验 `statSync === offset`，重复分片会被拒但没有幂等语义）。

### 证据
`tests/import-batch-chunks.test.ts`（8 例）：

- 顺序拼接成功 + 全量重放被识别为 `replayed`；
- 跳片拒绝且文件长度不变；
- 相同重放幂等、不同重放拒绝、跨界重叠拒绝；
- 超出声明大小拒绝；
- 乱序拼接后旧区间重放拒绝（写入位置即事实）；
- 只上传一部分 → `start()` → `needs_reselect` 且书架为空（不会带病导入）；
- 重选后恢复同一 item；
- ZIP：跳片 / 不一致重放 / 跨界重叠三种都拒绝。
