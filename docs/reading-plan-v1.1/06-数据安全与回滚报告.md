# 06 · 数据安全与回滚报告

## 1. 写入路径没有变

```ts
change(action):
  ensureOpen()                        // 未挂载一律拒绝
  if (this.archiving) throw           // 归档期间禁止写
  draft = structuredClone(state)      // 副本
  result = action(draft)              // 任何 throw 都不会走到落盘
  history.prepare(draft)
  atomicWrite(library.json, {...prepare(draft), schema: 8, tasks: [], episodes: [], $history})
      openSync(tmp,'wx') → writeFileSync → fsyncSync → renameSync
  state = history.bind(draft, ref)
```

动作抛错 → 快照不动；落盘抛错 → 内存态不换，重开读到旧快照。

## 2. 三个单点提交（本轮新增/重写）

| 场景 | 一次提交内的内容 |
| --- | --- |
| 完读交接 `completeCurrentPlanned` | `archiveItem(completed)` + `invalidate` + `selected` + `startedAt` |
| 停止当前书 `removeFromPlan(stop)` | `archiveItem(skipped/removed)` + `invalidate` + `selected` + `startedAt` |
| 自主选书入队 `addToPlanAtomic` | intent 回执 + 计划条目 |

`plan-stop-atomic`「leaves nothing behind when the commit fails」用注入式 `write` 在提交边界抛 `disk full`，断言：条目仍在 `items`、归档为空、`selected` 未变、`confirmedChars` 未变；随后重试成功。这是"任意写入失败都不会留下半截状态"的直接证据。

## 3. 磁盘预算：拒绝在写入之前

| 限制 | 值 | 检查点 |
| --- | --- | --- |
| 单文件 | 100 MiB | `addItems`（声明期）、`stage`（分片期）、ZIP 条目 |
| 单批条目 | 100 | `addBatchItems` |
| 单批暂存总量 | 1 GiB | `addItems`（累计）、`stage`（每次复核） |
| 同时解析 | 2 | `dispatchable()` |
| ZIP 原始体 | 512 MiB | `zipBegin` + 每个 `zipChunk` |
| ZIP 展开后 | 1 GiB | 传给 hardened worker 的 `maxTotalBytes` + 展开后再校验 |

`import-batch-budget`「accepts 100 files and reports the 101st as overflow without staging it」同时断言**暂存目录里 0 个 `.src` 文件**——超限的那本一个字节都没写。

## 4. 分片完整性（含清理安全）

`stage()` / `zipChunk()`：

- append-only：写入位置只能是文件当前真实长度；
- 跳片 → 拒绝；跨界重叠 → 拒绝；
- 重复分片只有在**逐字节一致**时幂等接受，否则拒绝；
- 每次写完 `statSync` 校验长度；
- 最后一片落盘后才 `pump()`，`launch()` 再复核一次真实长度，不符转 `needs_reselect`。

清理：

- `cleanStale()` 只处理"名字是 UUID 且属于已知批次"的目录；不属于任何已知批次的目录才整体删除（那本来就是本模块留下的）。
- 批次目录内只识别 `<uuid>.src`、`source.zip`、`<uuid>.import/`、`*.extract` 四种形状，其余文件一律不碰。
- `forgetImportBatch` 只删记录；`cleanStale` 随后只清该批次自己的目录。`import-batch-budget`「never deletes a directory it did not create」用一个外来目录 `someone-elses-data` 验证不被误删。

## 5. 降级保护（fail-closed）

- 文件布局提升到 **8**；v0.66.7 只认 `5/6/7`，读到 8 时 `validateState` 抛错 → `open()` 失败 → 库打不开，不会写任何东西。
- 升级提交失败时 `library.json` 字节不变（SHA-256 对比用例）。
- 备份/恢复（JSON 与 `.bfbak`）都带回计划顺序。

代价：降级期间库不可用。这是审核允许的选项，也是本仓库唯一可行的 fail-closed 手段。**回滚前必须用新版本导出备份。**

## 6. SSM 守卫：需要人工确认（未自行放行）

```
$ corepack pnpm check:ssm
  REVIEW  src/library.ts   [src/library.ts]
  REVIEW  src/world.ts     [src/world.ts]
结论: blocked=0 review=2 allowed=51
exit=1
```

原因：这两个文件本来就含 SSM（故事记忆）共享区段，`check:ssm` 对任何改动都要求 SSM 负责人确认。本轮在 `src/library.ts` 增加的是计划与批次方法（`completeCurrentPlanned` / `startPlanned` / `nextReadable` / 计划与批次 API），在 `src/world.ts` 增加的是 `plan` 面板、批量导入方法与 plan 摘要——**没有修改 `src/story/**`，也没有改动 SSM 的读写语义**。

我**没有**使用 `--accept-review` 自行放行：那等于伪造负责人同意。请 SSM 负责人按流程确认：

```bash
corepack pnpm check:ssm --accept-review "已获得 <负责人> 同意：<范围与理由>"
```

## 7. 与正式用户数据的关系

- 所有测试库都在 `mkdtempSync(tmpdir())` 下，结束 `rmSync`。
- 本轮没有对任何真实 `dataDir` / `library.json` / `history.sqlite` / `AcquisitionRecords` 执行写操作。
- 未启用 GC、未触发数据迁移脚本、未 `push`/`merge`/发布/部署。

## 8. 越权面收敛

| 面 | 措施 |
| --- | --- |
| 模型 | 未新增工具；计划编辑只在 WebUI；协议文档明确"顺序由用户决定" |
| WebUI | 所有批次方法要求显式 `batchId`/`itemId`；`stage` 校验连续偏移与 base64 往返；`reselect` 校验条目状态与文件长度 |
| 文件 | 文件名过 `safeBatchName()`（拒 `..`、控制字符、`<>:"\|?*`）；ZIP 条目过既有 `zip-worker` 全套校验 |
| 停止/跳过 | 停止当前阅读必须 `stop: true` + 面板二次确认；普通移除当前书抛错；完读条目拒绝被改写 |
