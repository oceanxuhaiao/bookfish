# 三、第一阶段：P1-1 暂存目录安全与符号链接防护

**优先级：最高。**

涉及：

- `src/txt-acquisition/staging.ts`
- `src/txt-acquisition/acquisition.ts`

## 3.1 已发现的问题

当前实现对 `verifiedOriginal()` 中的目录符号链接进行了检查，但其他操作路径没有统一执行目录真实性验证。

涉及：

- `init()`
- `clearAbandonedPrepared()`
- `clearExpiredParts()`
- `enforceQuota()`
- `commitRaw()`
- `dropRaw()`

目前 `resolveInside()` 主要解决路径字符串逃逸问题，不能证明实际目录没有被 junction 或 symlink 重定向。

如果 workDir/rawDir 指向获取目录之外的目录，清理和提交操作可能影响外部文件。

## 3.2 修复要求

建立统一目录安全检查机制，例如：

`assertSafeDirectories()`

具体命名可以调整。

要求：

1. root、rawDir、workDir 必须位于预期目录。
2. 目录不能是未经授权的符号链接或 junction。
3. 必须考虑 Windows NTFS reparse point。
4. 检查必须发生在任何清理、提交、配额回收之前。
5. 检查失败时立即 fail-closed。
6. 不得继续执行后续文件删除或写入。
7. 检查不能仅依赖字符串路径比较。
8. 防止检查后路径再次被替换。

对于无法在现有平台接口下彻底消除的目录替换竞争，必须明确记录残余风险，不能声称已经完全防护。

## 3.3 必须新增测试

| 测试 | 操作 | 预期 |
|---|---|---|
| D01 | rawDir 指向外部 symlink | 拒绝操作 |
| D02 | workDir 指向外部 symlink | 拒绝操作 |
| D03 | root 路径存在重定向 | 拒绝操作 |
| D04 | Windows junction 替换 workDir | 拒绝操作 |
| D05 | junction 替换 rawDir | 拒绝操作 |
| D06 | 外部目录存在过期 .part | 不得删除 |
| D07 | 外部目录存在 .prepared.txt | 不得删除 |
| D08 | 外部目录存在 .verified.txt | 不得删除 |
| D09 | 外部目录存在超配额 TXT | 不得删除 |
| D10 | 检查过程中目录被替换 | 不得继续危险操作 |

至少保留 POSIX 符号链接测试和 Windows junction 测试。

**验收条件：获取目录以外的任何文件都不得因 BookFish 清理操作而被修改或删除。**

# 四、第二阶段：P1-2 共享原件与配额清理并发竞态

涉及：

- `src/txt-acquisition/acquisition.ts`
- `src/txt-acquisition/staging.ts`
- `src/txt-acquisition/records.ts`

## 4.1 已发现的问题

目前有：

- 活跃任务保护。
- SHA-256 引用保护。
- 清理前引用检查。
- `dropRaw()` 删除保护。
- 配额自动清理。

但引用检查与实际 `rm()` 不是原子操作。

可能出现：

1. 清理检查原件没有引用。
2. 检查通过。
3. 新任务提交相同 SHA-256 原件。
4. 新任务建立引用。
5. 旧清理任务继续执行 rm。
6. 新任务引用的原件被删除。

现有 `maintenance` Promise 串行化不足以保护 `commitRaw()` 和 `dropRaw()`。

## 4.2 修复要求

建立统一的提交和回收协调机制。

必须纳入：

- `commitRaw()`
- retained 引用持久化。
- `dropRaw()`
- `enforceQuota()`

可以采用：

- 统一异步互斥锁。
- 安全的文件回收隔离机制。
- 或其他能证明引用和删除一致性的方案。

不要仅通过重复调用 `canDelete()` 解决。

必须避免：

- 删除唯一原件。
- 引用已提交但原件不存在。
- 两个任务共享原件时其中一个任务清理影响另一个。
- 任务状态与文件实际存在状态不一致。

## 4.3 必须新增的竞争测试

### 测试 A：清理与新引用竞争

1. 创建 A、B 两个任务。
2. A 持有一个原始文件。
3. 暂停 `enforceQuota()` 在引用检查通过之后。
4. B 使用相同 SHA-256 提交原件。
5. B 完成引用持久化。
6. 恢复 A 的清理操作。
7. 验证原件仍存在。
8. B 必须能够成功 retry。

### 测试 B：dropRaw 与新引用竞争

同样使用 Barrier 控制执行顺序。

验证旧任务请求删除时，新任务能够安全取得原件引用。

### 测试 C：两个任务同时 commitRaw

验证不会产生：

- 文件内容错误。
- 引用丢失。
- 半成品覆盖。
- 哈希不匹配。

### 测试 D：World 中断

在提交与引用持久化之间中断，重启后能够恢复，不删除唯一有效原件。

**验收条件：无论任务执行顺序如何变化，都不能删除仍被有效任务引用的唯一原始文件。**

# 五、第三阶段：P1-3 awaiting_choice 重启后错误进入阅读队列

涉及：

- `src/selection.ts`
- `src/txt-acquisition/acquisition.ts`

## 5.1 已发现的问题

目前身份不完全匹配时：

```text
status = awaiting_choice
```

但 `queueOnImport` 默认仍可能为 true。

`reconcileQueue()` 的排除列表没有包含 `awaiting_choice`。

导致：

1. 小说身份不确定。
2. 导入后进入书架。
3. 当前没有加入阅读队列。
4. World 重启。
5. Selection 恢复。
6. `reconcileQueue()` 可能重新加入阅读队列。

这违反了身份未确认不得自动承诺阅读的产品规则。

## 5.2 修复要求

同时处理：

1. 身份不确定时，持久化 `queueOnImport=false`。
2. `reconcileQueue()` 明确排除 `awaiting_choice`。
3. 只有明确候选确认或用户明确决定后，才能恢复排队。
4. 恢复过程不能自动将 partial identity 转换为 exact。
5. 书籍可以保留在书架，但不能自动进入阅读队列。

## 5.3 必须测试

```text
创建 Selection Intent
→ 导入 partial identity 小说
→ 状态 awaiting_choice
→ 持久化
→ 停止 World
→ 创建新 SelectionCoordinator
→ recover()
→ reconcileQueue()
→ 阅读队列仍然为空
```

随后：

```text
用户明确确认候选
→ 更新身份确认状态
→ 允许排队
→ 进入阅读队列
```

还要测试连续两次 World 重启。

**验收条件：身份未确认的小说不会因为任何自动恢复流程进入阅读队列。**

# 六、第四阶段：P1-4 abandon/cancel 终态保护

涉及：

- `src/selection.ts`

## 6.1 已发现的问题

`abandon()` 将意图设置为 abandoned。

但 `onExternalImport()` 没有对 abandoned 做完整终态保护。

迟到的导入回调仍可能调用 `fulfill()`，使原本放弃的意图重新变成 reading。

这违反用户已经结束选书承诺后的行为预期。

## 6.2 修复要求

统一定义 Selection 终态转换规则。

至少保护：

- abandoned
- cancelled
- completed
- failed

禁止 `fulfill()` 无条件覆盖终态。

必须考虑：

- 正在下载时用户放弃。
- 下载完成但尚未入架时用户放弃。
- 已入架但回调尚未完成时用户放弃。
- World 重启后迟到回调。
- 重复回调。
- 同一个意图被多个异步操作完成。

放弃后可以保留已经入架的书籍，但不能重新进入自动阅读队列。

## 6.3 必须测试

| 场景 | 预期 |
|---|---|
| abandon 后下载完成 | 不重新排队 |
| abandon 后导入完成 | 不重新排队 |
| abandon 后回调迟到 | 不改变终态 |
| abandon 后 World 重启 | 仍然 abandoned |
| cancelled 后重复 fulfill | 拒绝 |
| 同一回调重复执行 | 不重复入队 |

**验收条件：用户明确放弃的选书意图不能被迟到异步操作重新激活。**

# 七、第五阶段：P1-5 Selection 与 TXT 获取取消联动

涉及：

- `src/selection.ts`

# 九、第七阶段：P1-7 Snapshot 与 commitRaw 的 TOCTOU

涉及：

- `src/txt-acquisition/staging.ts`
- `src/txt-acquisition/acquisition.ts`
- `src/stream-import.ts`

## 9.1 已发现的问题

`verifiedOriginal()` 已经做了：

- 原件 lstat。
- dev/inode/size/mtime 检查。
- Snapshot 复制。
- SHA-256 计算。

但是返回的是路径，而不是已经固定身份的文件句柄。

后续解码器重新通过路径打开 Snapshot 时，没有重新与原始 `task.file.sha256` 比对。

如果 Snapshot 在两次操作之间被同用户其他进程替换，可能出现读取了一个内容不同但自身稳定的文件。

`commitRaw()` 的：

```text
hashFile(temporary)
→ link(temporary, target)
```

也应检查类似的替换窗口。

## 9.2 修复要求

优先选择：

- 将已验证文件句柄传递给解码器。
- 或对解码实际读取的同一个文件句柄重新计算 SHA-256。
- 或使用其他能够证明实际读取字节与任务原始哈希一致的方案。

不能仅依赖路径和自身 inode 稳定性。

同时检查：

- 临时文件创建权限。
- 文件替换竞争。
- 硬链接提交。
- Snapshot 生命周期。
- 清理与解码并发。

## 9.3 必须测试

1. `verifiedOriginal()` 成功。
2. 在解码器打开之前替换 Snapshot。
3. 执行 retry。
4. 必须拒绝。
5. 原始哈希记录不变。
6. 不得将替换内容导入书架。

还要测试：

- commitRaw 哈希完成后替换临时文件。
- 链接提交失败。
- 磁盘空间不足。
- 同哈希目标文件已经存在。
