# 三、阶段一：数据可靠性缺陷修复

**授权状态：允许 Codex 自主实施。**

本阶段目标是修复能够实际触发的问题，完善失败恢复，不进行系统级网络改动。

对每个问题必须遵循：

**建立复现 → 确认问题 → 最小化修复 → 新增回归测试 → 验证旧行为不变。**

不能只根据推测修改正常代码。

## 3.1 原始文件完整性与失败重试

涉及：

- `src/txt-acquisition/acquisition.ts`
- `src/txt-acquisition/staging.ts`
- `src/txt-acquisition/records.ts`

当前 retry/repair 能从保留原件继续，但需要检查原件是否仍然完整。

### 实施要求

在重新导入前验证：

- 原始文件存在。
- 文件大小与任务记录一致。
- SHA-256 与记录一致。
- 文件可以读取。
- 路径没有逃逸暂存目录。
- 文件没有被替换为符号链接等不受信任对象。

如果原件被修改：

- 禁止静默导入。
- 记录清晰错误。
- 不覆盖原始哈希记录。
- 不删除其他有效副本。
- 保留可重新获取的任务信息。

### 必须测试

| 编号 | 情况 | 预期 |
|---|---|---|
| R3-01 | 完整原件 retry | 成功重试 |
| R3-02 | 原件修改一个字节 | 哈希不符，停止 |
| R3-03 | 原件截短 | 明确失败 |
| R3-04 | 原件不存在 | 可恢复状态或明确不可恢复 |
| R3-05 | 文件读取权限不足 | 报告存储错误 |
| R3-06 | retry 时 World 重启 | 任务可恢复 |
| R3-07 | repair 失败 | 不丢失原始文件 |
| R3-08 | 同一任务重复 retry | 不产生重复书籍 |

不得让文件系统错误被误判为小说质量差。

## 3.2 Selection 异步失败隔离

涉及：

- `src/txt-acquisition/acquisition.ts`
- `src/selection.ts`
- `src/library.ts`

当前代码已将文件导入成功与 Selection 回调失败分离。

本轮不需要重写，而是进行故障注入验证。

### 必须保证

1. 书籍持久化成功后，Selection 失败不改变入架结果。
2. Selection 失败有独立状态。
3. 重启后能够再次尝试队列接入。
4. 不重复创建阅读承诺。
5. 不重复下载同一原件。
6. 不重复创建同一 `bookKey` 的书架项。
7. 不自动推进阅读进度。

测试故意使以下步骤失败：

- `onExternalImport`。
- Selection 状态持久化。
- 阅读队列追加。
- announce。
- World 关闭时的异步回调。

验收条件：

**文件入架与阅读队列接入是两个独立结果，不会相互伪造成功或失败。**

## 3.3 原始文件保留与配额

涉及：

- `src/txt-acquisition/staging.ts`
- `src/txt-acquisition/acquisition.ts`
- `src/txt-acquisition/records.ts`

### 当前重点问题

`freeBytes()` 在 statfs 失败时返回极大值。

`prune()` 在清理异常时可能返回空数组，丢失具体错误。

这可能让磁盘不可用被误判为磁盘空间充足，或者让用户误认为清理成功。

### 实施要求

建立结构化的维护结果：

- success
- skipped_active_tasks
- over_quota_referenced
- permission_denied
- disk_unavailable
- cleanup_failed

具体字段由 Codex 根据当前项目规范实现。

必须区分：

- 没有文件需要删除。
- 存在引用所以不能删除。
- 正在执行任务所以暂不删除。
- 文件系统错误导致删除失败。

不得为方便实现直接吞掉全部异常。

### 共享原件保护

测试两个不同任务指向同一 SHA-256 原始文件：

1. A 完成且不再需要原件。
2. B 存在 warning 或等待 repair。
3. A 请求清理。
4. B 仍然能够读取原件。

此外需要验证：

- 清理期间任务重新获得引用。
- 同一哈希但不同格式扩展名。
- 任务记录损坏。
- 文件系统只读。
- 文件占用。
- 磁盘空间不足。

**绝不允许为了满足配额上限删除唯一可恢复原件。**

## 3.4 100任务限制

涉及：

- `src/txt-acquisition/types.ts`
- `src/txt-acquisition/records.ts`
- `src/txt-acquisition/acquisition.ts`

当前设计实际上区分：

- 100个活跃任务上限。
- 历史终态记录的软限制。
- 需要保留原件的历史任务不强制删除。

本轮首先明确并文档化这三个概念。

### 验收

- 100个活跃任务时，第101个不能创建。
- 并发请求不能突破活跃任务限制。
- 已完成、无引用的旧任务可以安全淘汰。
- 有保留原件引用的记录不能因为软上限被删除。
- 任务总记录超过100但均需要保留时，允许明确的受控超限状态，不应删除重要数据。
- 状态存储失败时不能报告创建成功。
- 容量不足时应明确提示，而不是创建孤儿任务。

必要时增加历史记录分页或归档机制，但不得引入第二套不兼容任务状态系统。

## 3.5 流式解码边界

涉及：

- `src/stream-import.ts`
- `src/txt-acquisition/repair.ts`
- `src/txt-acquisition/quality.ts`

当前已有流式解码，必须优先验证边界正确性。

### 测试矩阵

| 编号 | 输入 | 要求 |
|---|---|---|
| S01 | UTF-8 汉字跨块 | 不丢字 |
| S02 | GB18030 字符跨块 | 不乱码 |
| S03 | UTF-16LE/BE 跨块 | 不错位 |
| S04 | 完整 UTF-8 BOM | 正确处理 |
| S05 | BOM 与编码声明冲突 | 按明确规则处理 |
| S06 | CRLF 跨块 | 不重复换行 |
| S07 | EOF 单独 CR | 正确规范化 |
| S08 | 开头连续空白 | 不损坏正文 |
| S09 | 末尾数块全为空白 | 正确截断 |
| S10 | 文件全部为空白 | 明确拒绝 |
| S11 | 最后一个汉字截断 | 尽量保留前文并警告 |
| S12 | 恰好100MiB | 按文件大小规则处理 |
| S13 | 100MiB+1字节 | 拒绝 |
| S14 | 读取过程中增长 | 安全拒绝 |
| S15 | 读取过程中缩短 | 检测文件变化 |
| S16 | 写入失败 | 清理临时文件并保留原件 |

特别检查：

- 质量统计的字符数量。
- 实际索引的字符数量。
- 原文片段是否完整。
- 第一段与最后一段是否被错误截断。
- 是否出现重复分段。

不得仅使用“导入返回成功”作为验收。

## 3.6 混合编码保护

当前实现已不再单纯采用“替换字符最少”的全局编码选择。

这一设计必须保留。

新增样本：

- UTF-8 前半部 + GBK 后半部。
- GBK 前半部 + UTF-8 后半部。
- 多个交替编码段。
- UTF-8 正文中夹杂少量坏字节。
- 编码转换位置接近文件头。
- 编码转换位置接近文件尾。

验收重点：

**修复不能把原本正确的前文变成乱码。**

如果无法安全恢复另一编码段：

- 允许 warning / partial。
- 保留原件。
- 明确指出可读范围。
- 不宣称全本修复成功。

本轮不强制开发复杂的自动分段编码重建算法。只有确实存在可靠方案和测试证据时才实施。

## 3.7 HTML charset 处理

涉及：

`src/txt-acquisition/html-encoding.ts`

保持优先级：

BOM → HTTP charset → HTML meta → UTF-8/GB18030 回退。

覆盖：

- BOM 与 HTTP 冲突。
- HTTP 与 meta 冲突。
- GBK/GB2312 标签别名。
- meta 大小写与引号变体。
- meta 接近探测窗口边界。
- 无效 charset。
- 无 charset 的 UTF-8。
- 无 charset 的 GB18030。

要求所有实际使用 HTML 的下载和浏览器发现路径采用一致的处理逻辑。

TXT 原始字节不受 HTML 解码修改。

## 3.8 取消、清理与原子提交

涉及：

- `src/txt-acquisition/acquisition.ts`
- `src/txt-acquisition/bridge.ts`
- `src/txt-acquisition/staging.ts`

## 4.1 Node 网络下载安全

涉及：

- `src/txt-acquisition/url-policy.ts`
- `src/txt-acquisition/pinned-http.ts`
- `src/txt-acquisition/download.ts`

必须证明：

1. DNS 返回的全部 A/AAAA 答案都经过检查。
2. 任一答案为禁止地址时按既定策略拒绝。
3. 使用经过验证的 IP 建立 socket。
4. 不在建立连接时偷偷重新解析域名。
5. TLS SNI 与 Host 保持正确。
6. 逐跳处理重定向。
7. 不通过连接池复用未经检查的连接。
8. 拒绝特殊用途 IP。
9. 拒绝回环、内网、链路本地及云元数据地址。
10. 拒绝未授权端口。
11. 网络权限撤销后不能继续发起新请求。

新增最小安全矩阵：

- IPv4。
- IPv6。
- IPv4-mapped IPv6。
- 多答案混合。
- DNS 重绑定模拟。
- 多级重定向。
- HTTP 到 HTTPS。
- HTTPS 到 HTTP。
- 公网域名重定向到内网。
- 超时与取消。

不得用“URL校验通过”替代真实 socket 地址检查。

## 4.2 MV3 下载协议

涉及：

- `extension/background.js`
- `src/txt-acquisition/bridge.ts`

验证：

- 原始字节不被文本解码。
- 4MiB 分块及尾块正确。
- ACK 代表服务端实际接受。
- 分块序号连续。
- 租约过期后旧消费者不能继续提交。
- 新 Attempt 不接收旧 Attempt 的上传。
- 双消费者不会同时写入同一文件。
- 下载后磁盘 SHA-256 正确。
- token 变更后旧会话失效。
- port 变更后旧连接中止。
- 取消后不能产生 completed。
- 来源权限撤销立即停止任务。

测试：

- 两个浏览器同时连接。
- 旧 Consumer 延迟上传。
- 文件传到99%后断开。
- 桥接重启。
- 扩展重启。
- 浏览器重启。
- 浏览器下载 HTTP 错误。
- 服务端写盘错误。

## 4.3 正常用户授权与实验预批准

必须区分：

- 开发环境预批准。
- 扩展管理页授权。

## 4.4 浏览器就绪必须失败关闭

重点复核：

- `controllerReady`
- `browserReady`
- `transportConnected`

要求：

- controller 未安装 → 不可用。
- controller 失联 → 不可用。
- 保护规则失效 → 不可用。
- 代理不可用 → 不可用。

**严禁使用永久返回 true 的 stub 接入正式 World。**

# 五、阶段三：隔离宿主与真实小说验收

**授权状态：允许在非生产数据副本中进行普通用户权限级测试。**

涉及管理员权限、系统网络修改、正式 WFP 规则、VM 启用或日常浏览器登录态的操作，必须另行授权。

## 5.1 建立隔离宿主

优先使用主电脑现有 Coopanion 安装，但必须隔离测试数据。

要求：

- 独立测试 BookFish 实例。
- 独立数据目录。
- 独立测试书架。
- 独立日志目录。
- 独立网络测试配置。
- 不复用生产书架。
- 不直接修改生产 SSM 数据。

先完成数据备份与恢复演练。

如果 Coopanion 不支持同机独立实例，应优先使用测试副本或受支持的独立宿主环境，不得在不确认数据位置的情况下覆盖当前安装。

## 5.2 真实 Coopanion 基础验收

必须真实操作宿主，而不是仅调用 FakeHost。

检查：

1. World 成功加载。
2. API 6 契约正常。
3. 配置页正常。
4. 新工具注册正常。
5. `status` 返回准确状态。
6. controller 缺失时保持失败关闭。
7. 关闭网络权限后正常拒绝。
8. 原有书架可以读取。
9. TXT 文件可以通过隔离导入入口入架。
10. 书籍可以建立分段索引。
11. 阅读队列不会重复。
12. 重新启动宿主后状态保持。
13. 原有书源模块仍可运行。
14. 原有阅读与 SSM 功能不变。

在控制器未实现时，不得为了测试浏览器流程而直接解除安全门禁。

## 5.3 浏览器链路的隔离联调

如果已经具备经过批准的临时隔离实验环境，可以进一步验证：

资源页面 → MV3 → 桥接 → 原始文件 → 宽松导入 → 隔离书架。

必须保留：

- 页面地址及授权来源。
- 实际传输路径。
- 原始字节数量。
- SHA-256。
- 下载任务状态。
- 导入质量报告。
- 书架结果。
- 失败恢复记录。

这一实验不等于正式 Coopanion 产品控制器完成。

若没有经过批准的可强制隔离环境，则跳过浏览器真实派发测试，保留 `browserReady=false`，将其判定为环境阻塞，而不是通过模拟 Guard 绕过。

## 5.4 真实小说验证

目前只有：

**一份《红楼梦》原文 + 11份派生样本。**

本轮必须补充至少两类独立真实数据：

### A. 不同来源的合法小说

选择具有合法获取权限、结构不同的实际作品。

至少覆盖：

- 章节结构规范。
- 无标准章节标题。
- GBK/GB18030。
- UTF-8。
- 短篇文本。
- 长篇文本。

### B. 用户过去实际遇到的失败样本

如果用户提供旧版本曾拒绝、但人工判断质量尚可的 TXT：

优先纳入回归集。

不得将其作为要求用户进行额外人工标注的前置条件。

Codex 应当自动分析编码、结构和导入原因，并提供简明报告。

## 5.5 质量验收指标

至少统计：

- 文件获取成功率。
- 下载字节一致率。
- 实际导入成功率。
- 可恢复失败比例。
- 修复成功率。
- 错误拒绝样本数量。
- 错误接受样本数量。
- 正文缺失情况。
- 索引错误情况。
- 人工可读性观察结果。

同一作品的派生样本只能计为鲁棒性测试，不得当作不同真实小说数量。

混合编码只能局部可读时必须标记 partial。

缺章识别应覆盖中文数字章节，但不得声称仅凭 TXT 章节编号就能证明全本完整。

## 5.6 confirmedChars 与 SSM

每一本新导入小说必须满足：

- `confirmedChars = 0`。
- 不创建虚假的阅读回执。
- 不自动生成已读 Episode。
- 不向 Persona Memory 注入未读内容。
- 不把获取成功写成阅读成功。
- Story Index 只能基于后续真实阅读产生证据或按既定架构建立可回查索引。

# 八、阶段六：产品控制器架构方案

**本阶段仅授权调研、设计和必要的非侵入式代码分析。**

不授权实现正式管理员服务、持久 WFP 规则、正式安装器或系统网络配置变更。

## 8.1 必须比较两个方案

### 方案 A：宿主机独立浏览器 + WFP

内容：

- 独立 exe。
- 独立 profile。
- 独立来源权限。
- 代理和桥接双精确端点。
- 专用 WFP provider/sublayer。
- 最小权限管理员服务。
- 规则持久化与恢复。
- 浏览器升级校验。
- DNS 共享服务边界。

必须重点回答：

Windows Dnscache 作为共享系统服务代发 DNS 请求时，怎样做到可验证、可强制、不会影响全机其他应用的隔离？

不能用启动参数代替答案。

### 方案 B：独立 VM + 受控代理

内容：

- 独立浏览器。
- 独立操作系统网络空间。
- 专用虚拟网卡。
- 只能访问受控代理和必要桥接通道。
- 禁止默认 NAT 直接公网访问。
- DNS 只能经过可验证路径。
- 宿主和虚拟机间文件共享受限。
- 独立升级和回滚。

不能默认 VM 天然安全。

## 8.2 比较指标

至少给出：

| 指标 | 需要分析 |
|---|---|
| 网络隔离 | 能否形成强制边界 |
| DNS | 是否存在共享服务绕过 |
| 安全证据 | 可否重复验证 |
| 用户体验 | 安装和日常操作复杂度 |
| 资源占用 | 内存、CPU、磁盘 |
| 管理员权限 | 需要哪些操作 |
| Windows 兼容性 | 版本与功能要求 |
| 运行维护 | 浏览器与系统更新 |
| 失败恢复 | 崩溃、重启、断电 |
| 回滚卸载 | 能否完整恢复 |
| 普通用户使用 | 来源授权与登录流程 |

## 8.3 正式控制器状态机

设计至少包含：

- uninstalled
- installing
- protected
- browser_ready
- fail_closed
- recovery_required
- upgrading
- uninstalling

每个状态必须定义：

- 进入条件。
- 退出条件。
- 可以执行的操作。
- 失败后的动作。
- 网络规则应有的状态。
- 是否允许向浏览器派发任务。
- 是否需要管理员权限。

特别验证：

- 服务崩溃。
- 代理崩溃。
- 桥接崩溃。
- 浏览器崩溃。
- 系统重启。
- 浏览器更新。
- 安装中断。
- 卸载中断。
- 规则写入不完整。
- manifest 损坏。
- 版本回滚。

## 8.4 授权边界

即使方案完成，也不得自行：

- 启用 Hyper-V 或 Sandbox。
- 安装管理员服务。
- 修改 Windows 防火墙默认策略。
- 修改系统 DNS。
- 安装持久 WFP 规则。
- 启动正式网络隔离服务。
- 修改日常浏览器配置。
- 安装根证书。
- 访问用户日常浏览器 Cookie。

此阶段最终只提交：

**《BookFish 浏览器安全控制器：WFP 与 VM 技术选型报告》**

由用户决定下一阶段采用哪种方案。

遇到以下情况必须停止相关部分：

1. 当前工作区存在可能被覆盖的未提交成果。
2. 必须修改生产书架才能完成测试。

- 已完成内容。

5. 多个任务和浏览器同时运行时是否存在数据竞争？
6. Node 下载通道是否满足网络安全边界？
7. 浏览器缺少控制器时是否始终失败关闭？
8. 真实 Coopanion 中哪些功能已经通过，哪些仍然被安全门禁阻止？
9. 实际小说是否能够建立正确阅读索引？
10. 新书入架是否始终不伪造阅读进度？
11. 性能改动的内存收益与耗时代价是多少？
12. SSM 受保护行为是否得到负责人确认？
13. 采用 WFP 还是 VM 更适合正式产品？
14. 距离可发布状态还缺少哪些必要工作？

**只有以上问题有明确、可复核的结论，本轮才算完成。**

第三轮完成不自动意味着产品可以发布。

即使数据可靠性与隔离宿主测试全部通过，只要正式浏览器控制器、DNS 强制隔离、SSM 审核和生产部署验证未完成，就必须继续保持：

- `controllerReady=false`
- `browserReady=false`
- 不合并 main
- 不部署生产
- 不解除网络保护

**最终执行原则：保留已经完成的成果，优先修复实际问题；提高小说获取的容错能力，但不牺牲数据一致性、阅读真实性和用户电脑安全。**

Codex 在明确授权边界内连续自主执行，阶段末提交完整审核包，由独立审核决定是否进入下一阶段。
