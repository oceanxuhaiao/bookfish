# 04 · 批量超限与遗漏处理（P1-5）

对应任务书第 5 节。这是本轮最重要的产品验收项：**被拒绝的书不能从用户视野里消失。**

---

## 1. v1.3 的问题

`addItems()` 会返回五个拒绝桶（`duplicates` / `unsupported` / `tooLarge` / `overBudget` / `overflow`），但：

- ZIP 界面只读了 `unsupported`；`startFiles()` 只读了 `tooLarge` / `overBudget`；
- 这些拒绝结果**不落盘**，批次完成后无从查证；
- 更糟的是 ZIP 路径：解压后 `addItems` 只收下前 100 本 / 1 GiB，**成功解压就把 ZIP 删了**——超出的书既没入库、也没有任何东西留下，用户只看到"导入完成"。

## 2. 结果模型：`batch.rejected` + `status().report`

### 持久化结构（`src/import-batch.ts`）

```ts
export interface RejectedGroup { count: number; names: string[] }
export interface BatchRejected {
  unsupported: RejectedGroup; tooLarge: RejectedGroup; overBudget: RejectedGroup;
  duplicate: RejectedGroup; overflow: RejectedGroup;
}
```

- **计数永远精确**（跨多次 `add` 累加，跨重启保留）；
- 每个分类保留最多 100 个文件名用于展示（`REJECTED_NAME_LIMIT`），超出只影响"能看到多少名字"，不影响数字；
- `recordRejected()`（`:300`）在 `Library.addImportBatchItems()` 的**同一次原子写**里合并，不会出现"书进了批次、拒绝记录没写"的中间态。

### 报告视图（`batchReport()`，`:645`）

```ts
{
  accepted, shelfAdded, pending, failed, cancelled, needsReselect,
  duplicate, unsupported, tooLarge, overBudget, overflow,
  rejectedNames: { duplicate, unsupported, tooLarge, overBudget, overflow },
  incomplete,     // 任一拒绝/失败/待重选 → true
}
```

`status()` 现在始终返回 `report`，`accepted` 与 `shelfAdded` 分开：前者是"进批"，后者是"真上架"。

## 3. ZIP：先读清单，再决定要不要开始

### 中央目录预读（`readZipPlan()`，`src/import-batches.ts:98`）

在创建解压目录**之前**读取：

1. 文件尾 66 KiB 内找 EOCD（`0x06054b50`）；
2. 取中央目录偏移/大小/条目数；
3. 逐条读 `uncompressed size`、名字、目录标志；
4. 汇总：条目数、可导入本数（支持格式、非隐藏、非目录）、未压缩总量、最大条目。

**无法可信读取时返回 `null`**，调用方按最坏情况处理：

| 情况 | 处理 |
| --- | --- |
| ZIP64（`0xFFFF`/`0xFFFFFFFF` 逃逸值） | `null` → 用批次预算上限做预检 |
| 分卷归档 | `null` |
| 中央目录 > 8 MiB 或条目 > 20000 | `null` |
| 偏移越界 / 签名不符 | `null` |
| 读文件失败 | `null` |

"未知"绝不会被当成"很小"。

### 超限判定与行为

```ts
const books = Math.max(incoming, plan.supported);   // 重试时按已有条目折抵
if (books > BATCH_ITEM_LIMIT) {
  recordRejected(draft, { overflow: books - BATCH_ITEM_LIMIT, overflowNames: excessNames });
  throw this.fail(batchId, 'over_limit', `… ${books} 本 … 超过单批 100 本 … 请拆成多个批次 …`);
}
if (estimate > ceiling) throw this.fail(batchId, 'over_limit', `解压后约 … 超过本批可用 …`);
```

- **整包拒绝**，不导入前 100 本；
- **ZIP 原样保留**（`ready` + `failure = 'over_limit'`），不会删包；
- 报告里给出总数与名单（`rejectedNames.overflow` / `overBudget`）；
- 界面额外提示"压缩包已保留，请把这次要导入的书拆成多个批次；已入库的书不受影响"。

### 为什么不做"自动分批续导"

任务书允许提出更好的方案。评估后仍选"整包拒绝 + 提示拆分"，理由：

1. 自动分批需要把同一个归档解压 N 次（每次都要 512 MiB 峰值和一次完整哈希），磁盘与时间成本翻倍；
2. 分批边界（按文件顺序？按大小？）会决定哪些书进哪一批，属于产品决策，不该由导入器替用户决定；
3. 整包拒绝 + 明确清单让用户自己决定怎么分，且**原始 ZIP 始终是唯一事实来源**；
4. 已入库的书、`.src` 暂存、阅读进度在拒绝路径上完全不动（拒绝发生在 `mkdir` 之前）。

## 4. 多文件 / 文件夹导入

`startFiles()` 现在把服务端返回的五个桶全部读完，并补上客户端跳过（格式不支持）的数量：

```
1 个文件格式不支持，未导入；3 个文件超过单本 100 MiB，未导入；
2 个文件超出本批 1 GiB 预算，未导入；本次只接收了前 100 本，还有 20 本超出单批 100 本上限。
可以再点一次「选择多本 / 选择文件夹」导入剩余文件，已入库的书不受影响。
```

- 不再出现"只处理了前 100 本就显示全部成功"；
- 遗漏数量来自服务端 `overflow`，不是前端估算；
- 继续导入不需要特殊入口：再点一次按钮即可，已入库的书不会被重复导入（书名+作者身份去重）。

## 5. 完成态报告（界面）

`view.status !== 'preview'` 时固定渲染结果块：

```
本次结果：进批 100 本 · 已入库 98 本 · 等待 0 · 失败 2
未进入本批：重复或无效 3 个（甲.txt、乙.txt…）；格式不支持 1 个（封面.jpg）；
            超出单批 100 本上限 20 个（书101.txt…）
这些文件仍在你的磁盘上，没有进入阅读计划；需要的话可以再选一次，只导入没进来的部分。
```

`tests/webui/batch-import.test.ts` 断言了"未进入本批"、`重复或无效 1 个`、客户端跳过提示与"可以再点一次"。

## 6. 验收（任务书第 5 节）

| 场景 | 期望 | 用例 |
| --- | --- | --- |
| 99 / 100 本 | 正常导入，`overflow = 0` | `accepts exactly 100 books`（100 本边界） |
| 101 本（文件夹） | 进 100、`overflow = 1`、`incomplete = true` | `reports count overflow for a folder of 101 files` |
| 120 本（ZIP） | 整包拒绝、ZIP 保留、`overflow = 20` + 名单、0 条目 | `refuses 120 books instead of importing the first 100` |
| 累计恰好 1 GiB | 允许（预检 `estimate <= ceiling`） | 预算常量未改，见 `06` |
| 超过 1 GiB | 整包拒绝、ZIP 保留、报告完整 | `refuses an archive whose expansion exceeds the batch budget` |
| 混合重复 / 不支持 | 每个分类精确计数 + 名单，`incomplete = true` | `counts duplicates, unsupported, over-sized and over-budget files` |
| 界面呈现 | "本次结果"块 + "未进入本批" + 拆分提示 | 两个 UI 用例 |
