## 六个必须看的结论

1. **索引不可读时仍有第二道真实内容检查（P1-1）。** `readZipPlan()` 返回 `null`（ZIP64 / 中央目录 > 8 MiB / 条目 > 20000 / 分卷 / 结构不可信）时，`extractArchive()` 先把归档真实解压到一个独立 `.extract` 临时目录，再用**与上传路径完全相同的分类器** `classifyInputs()` 统计实际可导入书籍数与大小，满足才 `addItems()`，不满足则整包拒绝（`01`）。
2. **超限时零正式条目、零 `.src`、ZIP 字节不变（P1-1）。** 检查发生在 `addItems()` 之前；拒绝路径上不 `rename` 任何文件，`source.zip` 原样保留（SHA-256 与上传时一致），`.extract` 临时目录在 `catch` 中清理；已成功的其他批次完全不受影响（`01`、`02`）。
3. **第二道检查没有成为新资源漏洞（P1-2）。** 仍用 `workspaceBytes` / `batchBytes` 做预检；Worker 的 `maxTotalBytes` / `maxEntryBytes` 一字未改；解压到独立临时目录、确认前不正式暂存；未知格式不会被误算成可导入小说；绝不允许"先写入超额文件再检查"（Worker 在写第 N 个字节前就按声明大小中止）（`03`）。
4. **整包拒绝被结构化持久化（P2-3）。** `BatchZip.rejection` 记录 `kind` / `reason` / `measured` / 预估未压缩总量 / 可用预算 / 实际可导入数（未知为 `null`，绝不填 0）/ 已导入数 / `partiallyStaged: false` / `archiveKept: true` / 书目名单 / 下一步操作，并逐字段校验（`04`）。
5. **报告在任何批次状态都可见（P2-4）。** 条件从 `status !== 'preview'` 改为"存在任一已接受 / 重复 / 不支持 / 单本超限 / 预算超限 / 超 100 本 / 失败 / 取消 / 需重选 / 整包拒绝"；重启后 `state.error` 丢失也不再影响，因为报告来自持久化记录；历史批次重新打开显示同样内容（`05`）。
6. **客户端不再隐藏被过滤的文件（P2-5）、首次失败可原地恢复（P2-6）。** `startFiles()` 全量提交由服务端判定并持久化拒绝清单；`fail()` 保留原始错误后重读当前批次与历史摘要，刷新失败也不覆盖原错误，不需要关闭面板或重启宿主（`05`）。

## 本轮修复的真实缺陷（如实记录）

| 位置 | 性质 | 处理 |
| --- | --- | --- |
| `readZipPlan()` 返回 `null` 时的路径 | **安全缺口**（v1.4 遗留）：索引读不到时只有"用预算最坏值预检"一道闸门，101 本书的 ZIP64 只要解压后不超预算就会被接受，前 100 本入库、第 101 本静默失败 | 增加实际内容检查，超 100 本整包拒绝 |
| `classifyExtractionError()` 的错误码 | **真实 bug**（v1.4 遗留）：只匹配 `too_many_entries` / `entry_too_large`，而 Worker 实际抛 `zip_too_many_entries` / `zip_entry_too_large` → 解压炸弹被误判为 `transient` 并无限重试 | 正则改为真实错误码 |
| `readZipPlan` 的超大单本判定 | **一致性缺口**：用编译期常量 `MAX_BATCH_FILE_BYTES` 而非实际 `budget.fileBytes`，两值不同时预检与 Worker 判定不一致 | 改为传入 `budget.fileBytes` |
| `addNames()` 的计数 | **重复计数缺陷**：同一压缩包每次重试都把名单再加一遍，`overflow` 会随重试次数膨胀 | 按名去重后累计 |
| `startFiles()` 的客户端过滤 | **结果丢失**（v1.4 遗留）：`picked.filter(NOVEL)` 提前丢弃，被丢文件只活在一句临时错误里 | 全量提交，服务端分类并持久化 |
| `fail()` 只写临时错误 | **死路**（v1.4 遗留）：首次 ZIP 失败可能已有批次记录但 `view` 为空、历史列表也没刷新 → 无从操作 | 自动重读批次状态与历史摘要 |
