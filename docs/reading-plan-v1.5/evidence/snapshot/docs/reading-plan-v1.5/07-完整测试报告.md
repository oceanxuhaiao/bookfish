## 5. 本轮发现并修复的问题

| 问题 | 性质 | 处置 |
| --- | --- | --- |
| `classifyExtractionError()` 匹配 `too_many_entries` / `entry_too_large` | **产品 bug**：Worker 实际码是 `zip_too_many_entries` / `zip_entry_too_large` → 解压炸弹被判 `transient` 并无限重试 | 正则改为真实码 |
| `readZipPlan` 用编译期 `MAX_BATCH_FILE_BYTES` 判定超大单本 | **一致性缺口**：`budget.fileBytes` 不同时预检与 Worker 判定不一致 | 改为传入 `budget.fileBytes` |
| `addNames()` 不去重 | **计数错误**：同一包重试 3 次，`overflow` 从 20 变 60 | 按名去重后累计 |
| `validateZipRejection` 的 kind 白名单漏 `'entry'` | **校验缺口**：合法的单本超限记录被拒绝加载 | 补齐 5 个值 |
| `refuseArchive` 的 `names` 双重切片 | **语义混乱**：`[...names].slice(100).length ? names : names` 恒真 | 改为 `slice(0, REJECTED_NAME_LIMIT)` |
| `emptyAddResult()` 缺 `overflowNames` | TS2741 编译失败 | 补 `overflowNames: []` |
| `classifyInputs` 丢弃超限名单 | 功能缺口：`rejection.names` 为空 | 分类器内收集 `overflowNames`（上限 100） |
| 测试夹具 `Buffer` 不是 `BlobPart` | 测试类型错误（`Uint8Array<ArrayBufferLike>` vs `BlobPart`） | `Uint8Array.from(bytes)` 复制一次 |

没有为通过测试而放宽任何产品限制。有三处旧断言因**新规则更严**而失败并被改写（不是放宽）：

1. `webui/batch-import.test.ts` 两处文案（改为读报告块）；
2. `import-batch-zip-count-rules.test.ts` 的 4 项期望数组（默认 `sort()` 按 UTF-16 码元，`第` 在 `系` 前）；
3. 同文件的单本超限拆成两例（ZIP64 无法得知名字，普通 ZIP 可以）——这是**约束变清晰**，不是放宽。

## 6. 环境说明（与本轮代码无关）

- 项目 `vitest.config.ts` 用 `pool: 'forks'`。在本机 WorkBuddy 沙箱里，fork 子进程写模块缓存（`…/web/<hash>`）被 fs broker 拦下（`EPERM`），会偶尔吞掉个别测试文件并把整轮退出码变成 1。
- 因此全量证据日志使用 `--pool=threads` 运行（**同一套测试、同一份配置，仅换执行池**）：133 个文件全部执行、退出码 0。
- 作为交叉验证，本轮 5 个新增文件全部用 `--pool=threads` 逐个单独复跑通过；v1.4 起已用默认 forks 池验证过既有文件不受影响。
- 这是环境问题，v1.1–v1.5 都存在；不作为产品缺陷记录。
