# 02 · 整包拒绝与零副作用（P1-1 的行为面）

对应任务书第 1 节"超限时不许发生什么"。

---

## 1. 一个入口，两种来源

整包拒绝只有一个写入口：`ImportBatches.refuseArchive()`（`src/import-batches.ts:814`）。它的调用点共 6 处：

| # | 触发 | `kind` | `measured` | `books` |
| --- | --- | --- | --- | --- |
| 1 | 索引：可导入本数 > 100 | `count` | `false` | `plan.supported` |
| 2 | 索引：某条目 > `budget.fileBytes` | `entry` | `false` | `plan.supported` |
| 3 | 索引：`totalUncompressed > ceiling` | `bytes` | `false` | `plan.supported` |
| 4 | 实测：`verdict.overflow > 0` | `count` | `true` | `accepted + overflow` |
| 5 | 实测：`verdict.tooLarge.length > 0` | `entry` | `true` | `entries.length` |
| 6 | Worker 上限命中（`zip_too_large` / `zip_too_many_entries` / `zip_entry_too_large`） | `bytes` / `count` / `entry` | `false` | `null` |

`measured` 是这套设计的诚实标记：**索引说"120 本"和实测得"120 本"在数值上可能相同，但可信度不同**，界面因此分别写成"压缩包声明"与"解压后实测"。

第 6 种最需要留意：Worker 中止时从未产出 file list，所以 `books` 必须是 `null`。任务书第 3 节明令禁止把不可确定的数量伪装成精确数字——这里就是最容易被"顺手填个 0"的地方。

## 2. 拒绝时到底发生了什么（和没发生什么）

`refuseArchive()` 的全部副作用只有一个 `updateImportBatch`：

```ts
draft.zip.failure = failure;      // 'over_limit'
draft.zip.error = text;           // ≤500 字符的人类可读原因
draft.zip.rejection = rejection;  // 结构化记录
// count 拒绝额外写 rejected.overflow；entry 拒绝额外写 rejected.tooLarge
```

逐项对照：

| 对象 | 拒绝后状态 | 保证手段 |
| --- | --- | --- |
| `batch.items` | 长度不变（首次导入为 0） | 未调用 `addItems()` |
| `.src` 暂存文件 | 零个新增 | 拒绝发生在 `renameSync(from, to)` 循环之前；`refuseArchive` 内无 `rename` |
| `source.zip` | 存在、字节完全一致 | 不 `rmSync(zipPath)`；不重写文件 |
| `zip.state` | 仍是 `ready` | `refuseArchive` 不碰 `state` |
| `zip.sha256` | 不变 | 同上 |
| `.extract` 临时目录 | 已删除 | 调用点 4/5/6 在 `catch` 内，首句 `rmSync(target, {recursive:true, force:true})`；调用点 1/2/3 在 `mkdirSync(target)` 之前 |
| `lib.list()` | 长度不变 | 没有任何 `books` 写入 |
| 阅读计划 | 无新增条目 | 计划条目只能由 `ImportJob` 完成产生，而没有条目就没有 job |
| 其他批次 | 完全不受影响 | 只 `updateImportBatch(本批)` |
| `peakBytes` | 保留已测值（若有） | 不重置 |

`tests/import-batch-zip-unknown.test.ts:197` 一条用例同时断言前 5 项：

```ts
expect(existsSync(zipPath(batchId))).toBe(true);
expect(sha256(readFileSync(zipPath(batchId)))).toBe(digest);          // 上传时的摘要
expect(readdirSync(batchDir(batchId)).filter(n => n.endsWith('.src'))).toHaveLength(0);
expect(extractDirs(batchId)).toHaveLength(0);
expect(lib.list()).toHaveLength(0);
expect(lib.importBatches()[0].zip?.rejection?.accepted).toBe(0);
```

`tests/import-batch-zip-budget-integrity.test.ts:91` 进一步断言**批次目录里只剩下 `source.zip`**：

```ts
expect(readdirSync(batchDir(batchId)).sort()).toEqual(['source.zip']);
```

## 3. 为什么"拒绝发生在 rename 之前"是结构性的，不是约定

看 §2 的流程顺序就能看出这不是靠"记得别写"。解压结果落在 `batchDir/<uuid>.extract` 这个**独立临时目录**里，与 `.src` 暂存位是两个物理位置：

```
transfers/batches/<batchId>/
├── source.zip               ← 归档本体，拒绝时原样保留
├── <uuid>.extract/          ← 临时解压树，无论成败都 rmSync
└── <itemId>.src             ← 暂存位，只在 addItems + rename 阶段产生
```

要"部分导入"必须同时做到：① 分类器放行部分条目；② 对这些条目 `renameSync` 到 `.src`。而 ② 在代码里只有一个位置（`for (const item of mine.items)` 循环），只有走过 `addItems()` 才会进入——`verdict.overflow > 0` 直接 `throw`，永远到不了。所以"零 `.src`"是控制流的必然结果，不是额外维护的约束。

## 4. 已成功批次不受影响（含并发与重试）

三种容易出错的情形：

**a) 同一会话里先后导入两个包。** 每个包有独立 `batchId` 与独立 `batchDir`；`ceiling` 按本批目录实算（`existing = dirTreeBytes(batchDir) - zipSize`），不共享全局计数。第一个批次拒绝不改变第二个批次的任何金额。

**b) 同一批次重试。** `refuseArchive` 保留 `state: 'ready'`，所以面板仍给"重试解压"，`resume()` 在重启后也会再试（除非 `failure === 'over_limit'`，见下）。重试时 `acceptedBefore` 取当前条目数，`classifyInputs` 把已存在名字算作 `duplicates` —— 99 已暂存 + 归档补 1 本的用例（`tests/import-batch-zip-count-rules.test.ts:195`）恰好结束在 100 本、`report.duplicate = 99`。

**c) 重启后的自动重试。** `resume()` 对 `failure === 'over_limit'` 不解压（`tests/import-batch-zip-budget-integrity.test.ts:102` 断言 `report.archives === 0`）。理由：整包拒绝是确定性结论，重启不会让 120 本变成 100 本；反复解压一个必然被拒的包只会浪费一分钟 CPU 和一次 512 MiB 哈希。

## 5. 六种失败类型共享同一份恢复语义

`BatchZip['failure']` 的取值与可见恢复路径：

| `failure` | 含义 | `state` | 面板入口 | `resume()` |
| --- | --- | --- | --- | --- |
| `missing` | 归档文件不在 | `ready` | 重选压缩包 | 不重试 |
| `unverifiable` | 长度 / SHA-256 不符或缺失 | `ready` | 重选压缩包 | 不重试 |
| `over_limit` | 计数 / 字节 / 单本 / 数量上限 | `ready` | 重试解压（拆包后换包） | **不重试** |
| `disk` | 磁盘不足或无法测量 | `ready` | 释放空间后重试 | 重试 |
| `transient` | Worker 故障 / rename 拒绝 / 权限 | `ready` | 重试解压 | 重试 |

`over_limit` 与 `transient` 的分流依赖 Worker 的真实错误码，v1.4 在这里有一个真 bug（`01` §8 之外的第三个）：正则写的是 `too_many_entries` / `entry_too_large`，Worker 实际抛 `zip_too_many_entries` / `zip_entry_too_large`。后果不是文案错误——**一个解压炸弹会被归为 `transient`，然后每次 `resume()` 都重新解压一次**。v1.5 改正为：

```ts
if (typeof code === 'string'
  && /^(zip_too_large|zip_too_many_entries|zip_entry_too_large)$/u.test(code)) return 'over_limit';
```

## 6. 索引预检与实测的顺序（为什么两个都要）

三层闸门，成本递增：

```
第 1 层  索引预检（读 ≤8 MiB 中央目录）          成本：一次 statSync + 一次有界读
第 2 层  磁盘预检（dirTreeBytes + diskFree）     成本：一次目录递归
第 3 层  实际解压 + 内容检查                    成本：一次完整解压 + 一次 SHA-256
```

第 1 层能给出确定答案时就不做第 3 层（120 本的普通 ZIP 直接拒绝，不解压）；第 1 层读不到答案（`null`）时必须做第 3 层——这正是不把 `null` 当"小包"的全部含义。反过来，第 1 层读到"99 本"也不跳过第 3 层：索引只说"99 个支持格式的非隐藏条目"，但大小写重复、路径归一化后重复、单本超限、预算超限仍要在真实树上判。

## 7. 一致性：`rejection` 与 `report` 不会互相矛盾

`rejection` 是新的结构化记录，`rejected`（v1.4 引入的分类计数）继续存在。两者在拒绝路径上同时写：

- `kind === 'count'` → `recordRejected(draft, { overflow, overflowNames: rejection.names })`
- `kind === 'entry'` → `recordRejected(draft, { tooLarge: rejection.names })`
- `kind === 'bytes'` → 不写分类桶（字节超限不是"某些文件被拒"，是整个包放不下）

`addNames()` 同时改为按名去重累计（`src/import-batch.ts:196`）：

```ts
for (const name of names) {
  if (group.names.includes(name)) continue;   // 同一包重试不会重复计数
  group.count += 1;
  if (group.names.length >= REJECTED_NAME_LIMIT) continue;
  group.names.push(name.slice(0, BATCH_NAME_LIMIT));
}
```

否则同一个 120 本包重试 3 次，`report.overflow` 会变成 60——用户看到"60 本超出上限"而实际只有 20 本。这是任务的"计数准确"要求之外的一个真实数据错误。

`tests/import-batch-v15-compat.test.ts:98`（250 本）验证：名单只留前 100 个，`count` 仍是 250。
