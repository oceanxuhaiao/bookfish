# 04 · 拒绝结果的结构化持久化（P2-3）

对应任务书第 3 节。命题：**"整包被拒"必须是一个可复原的记录，而不是一句临时错误。**

---

## 1. v1.4 的问题

v1.4 已经有 `BatchZip.failure`（`'over_limit'`）与 `BatchZip.error`（≤500 字符文案）。够用吗？不够：

| 缺什么 | 后果 |
| --- | --- |
| 拒绝**类型** | `over_limit` 至少覆盖 count / bytes / entry 三种完全不同的原因 |
| **未压缩总量** | 用户不知道"到底多大" |
| **可用预算** | 用户不知道"差多少" |
| **可导入书籍数** | 唯一能指导"怎么拆"的数字，完全缺失 |
| **是否部分暂存** | 用户无法确认"我前面那 99 本还在不在" |
| **原始 ZIP 是否保留** | 用户不知道该重选还是该去找文件 |
| **下一步操作** | 只能靠读文案猜 |

而且 `error` 是瞬时字段：`fail()` 在刷新后可能被覆盖，面板重开时若报告块不渲染（P2-4 的 bug），用户就永久失去了这次拒绝的全部信息。

## 2. 数据结构

```ts
export type ZipRejectionKind = 'count' | 'bytes' | 'entry' | 'disk' | 'plan';

export interface ZipRejection {
  kind: ZipRejectionKind;
  reason: string;              // 人类可读，与 throw 的文案一致，≤500
  measured: boolean;           // 数字来自实测解压（true）还是归档声明（false）
  totalBytes: number | null;   // 未压缩总量；null = 未知
  budgetBytes: number | null;  // 当时本批可用字节；null = 未计算
  books: number | null;        // 可导入书籍数；null = 无法枚举
  limit: number;               // BATCH_ITEM_LIMIT（100），供界面直接引用
  accepted: number;            // 拒绝前本批已进批的条目数
  partiallyStaged: false;      // 类型级常量：整包拒绝永不部分暂存
  archiveKept: true;           // 类型级常量：整包拒绝永不删归档
  names: string[];             // 涉及的书籍名，≤100，每个 ≤260
  nextStep: string;            // 一句话下一步，≤500
}
```

### 为什么 `partiallyStaged` / `archiveKept` 是字面量类型

不是 `boolean`，而是 `false` / `true`。这让"整包拒绝却部分暂存"在**类型层面**无法表达，同时让 `validateBatches()` 的校验成为第二道防线（伪造的 `partiallyStaged: true` 会被拒绝加载）。任务书第 3 节要求"是否部分暂存"必须是记录的一部分——用常量而非变量是最强的表达。

## 3. `null` 不是 0（这条要单独说）

三个数字字段都允许 `null`：

| 字段 | `null` 的确切含义 | 何时为 `null` |
| --- | --- | --- |
| `totalBytes` | 归档未声明总量，且未实测 | Worker 上限中止（无 file list、无可用 plan） |
| `budgetBytes` | 未计算 | 当前所有调用点都会算，保留 `null` 供未来扩展 |
| `books` | **无法枚举** | Worker 上限中止；或索引不可读且解压未完成 |

界面对应两种措辞（`src/webui/batch-import.ts:479`）：

```ts
const claimed = archive.measured
  ? say(`解压后实测 ${archive.books ?? '未知'} 本 / ${archive.totalBytes ?? '未知'} 字节`, …)
  : say(`压缩包声明 ${archive.books ?? '未知'} 本 / ${archive.totalBytes ?? '未知'} 字节`, …);
```

任务书明令"不能把不可确定的数量伪装成精确数字"——所以是 `'未知'` 而不是 `0`。`0` 会被读成"这个包里一本书都没有"，是完全不同的结论。

同样禁止的是"制造虚假的 `overBudget` 文件数"：`kind === 'bytes'` 的拒绝**不写任何分类桶**：

```ts
if (kind === 'count' && detail.overflow) recordRejected(draft, { overflow: …, overflowNames: … });
if (kind === 'entry') recordRejected(draft, { tooLarge: rejection.names });
// kind === 'bytes' / 'disk' / 'plan'：无分类桶
```

字节超限不是"某些文件被拒"，是整个包放不下。如果硬塞 20 个文件名进 `overBudget`，报告会显示"20 个文件超出预算"，而实际原因是总量超限——这是编造的数字。

## 4. 六个调用点的字段填充

| # | 场景 | `kind` | `measured` | `totalBytes` | `budgetBytes` | `books` | `names` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 索引：本数 > 100 | `count` | `false` | `plan.totalUncompressed` | `ceiling` | `plan.supported` | `plan.supportedNames.slice(100)` |
| 2 | 索引：单本超限 | `entry` | `false` | `plan.totalUncompressed` | `ceiling` | `plan.supported` | `plan.oversizeNames` |
| 3 | 索引：总量超限 | `bytes` | `false` | `plan.totalUncompressed` | `ceiling` | `plan.supported` | `plan.supportedNames` |
| 4 | 实测：本数 > 100 | `count` | `true` | `outcome.bytes` | `ceiling` | `accepted + overflow` | `verdict.overflowNames` |
| 5 | 实测：单本超限 | `entry` | `true` | `outcome.bytes` | `ceiling` | `entries.length` | `verdict.tooLarge` |
| 6 | Worker 上限 | 按码 | `false` | `plan?.totalUncompressed ?? null` | `ceiling` | **`null`** | `plan ? (entry ? oversizeNames : supportedNames) : []` |

第 6 行 `books: null` 是刻意的。Worker 中止发生在条目遍历中途，`outcome.files` 根本不存在（`extractRuntimeZip` 直接 reject）。任何"用归档大小除一下"或"用 `maxEntries` 顶一下"的推算都是伪造。

第 6 行的 `names` 从 `plan` 取（若索引可读）：这是**仍然有效的证据**——索引确实告诉我们那些条目超限了，只是无法确认解压后的实际情况。这类"半可信"数据必须与 `measured: false` 同时出现，用户才能正确评估。

## 5. 持久化校验（`validateZipRejection()`，`src/import-batch.ts:794`）

加载时逐字段检查，任何一项不合法整批拒绝加载（不是丢弃字段继续跑——静默吞掉校验失败会让伪造记录看起来像真的）：

```ts
if (!['count', 'bytes', 'entry', 'disk', 'plan'].includes(String(value.kind))) throw new Error('Invalid archive rejection kind');
if (typeof value.reason !== 'string' || !value.reason || value.reason.length > 500) throw …;
if (typeof value.measured !== 'boolean') throw …;
for (const field of ['totalBytes', 'budgetBytes', 'books']) {
  const number = value[field];
  if (number !== null && (!Number.isSafeInteger(number) || number < 0)) throw new Error('Invalid archive rejection figure');
}
if (!Number.isSafeInteger(value.limit) || value.limit < 1) throw …;
if (!Number.isSafeInteger(value.accepted) || value.accepted < 0) throw …;
if (value.partiallyStaged !== false || value.archiveKept !== true) throw new Error('Invalid archive rejection invariants');
if (!Array.isArray(value.names) || value.names.length > REJECTED_NAME_LIMIT) throw …;
for (const name of value.names) if (typeof name !== 'string' || !name || name.length > BATCH_NAME_LIMIT) throw …;
if (typeof value.nextStep !== 'string' || !value.nextStep || value.nextStep.length > 500) throw …;
```

要点：

- 数字字段"要么 `null`，要么非负安全整数"——`-1` / `1.5` / `NaN` / `'10'` 全部拒绝；
- `names` 长度上限 100（`REJECTED_NAME_LIMIT`），每个名字 ≤260（`BATCH_NAME_LIMIT`）；
- 空字符串不算合法名字（`!name`）；
- `nextStep` 必须非空——一个"被拒绝但不知道下一步"的记录等于没有记录。

`tests/import-batch-zip-budget-integrity.test.ts:198` 用三条伪造记录验证：

```ts
expect(() => validateBatches([{ ...batch, zip: { ...batch.zip, rejection: { ...base, kind: 'nonsense' } } }])).toThrow('rejection kind');
expect(() => validateBatches([{ ...batch, zip: { ...batch.zip, rejection: { ...base, partiallyStaged: true } } }])).toThrow('invariants');
expect(() => validateBatches([{ ...batch, zip: { ...batch.zip, rejection: { ...base, books: -1 } } }])).toThrow('figure');
```

## 6. `report.archiveRejected`：只暴露给上层，不重复存

```ts
export interface ImportBatchReport {
  …
  /** Set when the whole archive was refused; null when it was not. */
  archiveRejected: ZipRejection | null;
}

export function batchReport(batch: ImportBatch): ImportBatchReport {
  …
  incomplete: … || batch.zip?.rejection !== undefined,
  archiveRejected: batch.zip?.rejection ?? null,
}
```

`report` 是派生视图，不落盘；`rejection` 只在 `batch.zip` 上存一份。这样"看到什么"与"存了什么"永远一致，不存在两份可能不同步的副本。

`incomplete` 也加了 `|| batch.zip?.rejection !== undefined`：即使所有分类计数都是 0（比如 `bytes` 拒绝不写桶），"整包被拒"也必须让 `incomplete === true`，否则报告会声称"完整"。

## 7. 重启后可见性（与 P2-4 的衔接）

`status()` 的 `zip` 视图透传 `rejection`：

```ts
const zip = batch.zip ? {
  name, size, state, …,
  ...(batch.zip.failure ? { failure: batch.zip.failure } : {}),
  ...(batch.zip.error ? { error: batch.zip.error } : {}),
  ...(batch.zip.rejection ? { rejection: batch.zip.rejection } : {}),
} : undefined;
```

因此：
- 面板关闭再打开 → `import_batch_status(batchId)` 重新读盘 → `rejection` 原样返回；
- 宿主重启 → `validateBatches()` 通过 → 同上；
- 历史批次列表 → `batchSummary()` 不带 `rejection`（列表不需要细节），但点进任一批次就能看到。

`tests/import-batch-zip-budget-integrity.test.ts:153` 做完整往返：

```ts
const reloaded = validateBatches(JSON.parse(JSON.stringify(lib.importBatches())), time);
expect(reloaded[0].zip?.rejection?.kind).toBe('count');
expect(reloaded[0].zip?.rejection?.measured).toBe(true);
expect(reloaded[0].zip?.rejection?.books).toBe(110);
expect(reloaded[0].zip?.rejection?.limit).toBe(100);
expect(reloaded[0].zip?.rejection?.partiallyStaged).toBe(false);
expect(reloaded[0].zip?.rejection?.archiveKept).toBe(true);
```

## 8. 名字窗口：精确计数 + 有限名单

`rejection.names` 上限 100（`REJECTED_NAME_LIMIT`）。与 `rejected` 各分类桶同一策略：**数字永远精确，名单只是展示窗口**。

- 120 本的包 → `books: 120`（精确）、`names` 是超出的 20 个（`supportedNames.slice(100)`）；
- 250 本的包 → `books: 250`、`names` 只留 100（`tests/import-batch-v15-compat.test.ts:98` 直接用 `rejected.overflow.count === 250` 验证同一策略）；
- 名字被 `slice(0, 260)` 截断（`BATCH_NAME_LIMIT`），否则超长路径会撑坏界面。

`readZipPlan()` 的 `supportedNames` / `oversizeNames` 本身也有 400 上限（避免 20000 条目的包把内存撑爆），`refuseArchive()` 再 `slice(0, 100)`，所以最终落地一定 ≤100。
