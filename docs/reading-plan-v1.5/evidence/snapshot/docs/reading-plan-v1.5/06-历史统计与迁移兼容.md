# 06 · 历史统计与迁移兼容（v1.1–v1.4 数据）

对应任务书第 7 节"旧阅读计划数据不受影响"。本轮**没有改** `ReadingPlan` / `statsComplete` / 任何迁移逻辑；本文档是验证记录，不是变更说明。

## 1. 本轮对数据模型的实际改动

只有一处是"新增"，没有任何"修改"：

| 结构 | 改动 | 性质 |
| --- | --- | --- |
| `BatchZip.rejection?: ZipRejection` | 新增可选字段 | 纯增量，缺省为 `undefined` |
| `BatchAddResult.overflowNames` | 新增必填数组 | 仅内存返回值，不落盘 |
| `ImportBatchReport.archiveRejected` | 新增派生字段 | 不落盘 |
| `BatchZipView.rejection?` | 新增可选字段 | 仅视图 |

**没有**改：`BATCH_SCHEMA`、`PLAN_SCHEMA`、`ImportBatch` 既有字段、`BatchRejected` 结构、`statsComplete` 语义、`validateBatches` 对既有字段的规则、`validatePlan`。

## 2. 三种历史数据快照的加载验证

`tests/import-batch-v15-compat.test.ts` 用手工构造的 JSON 快照（不是现版的 `newBatch()` 产物）验证三个年代的数据：

### 2.1 v1.3 批次：既无 `rejected` 也无 `failure`

```ts
const raw = base();
delete raw.rejected;                                  // v1.3 没有这两个字段
delete raw.zip.failure;
delete raw.zip.rejection;
const loaded = validateBatches([JSON.parse(JSON.stringify(raw))], NOW);
```

| 断言 | 结果 |
| --- | --- |
| `loaded[0].rejected` | `undefined`（不补空对象） |
| `loaded[0].zip.failure` | `undefined` |
| `loaded[0].zip.rejection` | `undefined` |
| `report.accepted` | `1` |
| `report.archiveRejected` | `null` |
| `report.incomplete` | `false` |
| `zip.sha256` | `'a'.repeat(64)`，原值不变 |

关键点：**不制造拒绝计数**。如果 `validateBatches` 给老批次补一个 `rejected: { count: 0, … }`，报告会显示"重复或无效 0 个"——看似无害，但会让"这份记录是 v1.3 的、当时根本没有拒绝统计"这一事实消失。所以缺省就是缺省。

### 2.2 v1.4 批次：有 `rejected` 与 `failure`，无 `rejection`

```ts
raw.rejected = { unsupported: { count: 2, names: ['封面.jpg', '说明.png'] },
                 tooLarge: { count: 0, names: [] }, overBudget: { count: 0, names: [] },
                 duplicate: { count: 1, names: ['甲.txt'] },
                 overflow: { count: 3, names: ['书101.txt', '书102.txt', '书103.txt'] } };
raw.zip.failure = 'over_limit';
raw.zip.error = '超出单批 100 本';
```

| 断言 | 结果 |
| --- | --- |
| `report.unsupported` | `2`，名单 2 项 |
| `report.duplicate` | `1` |
| `report.overflow` | `3`，名单 3 项 |
| `report.archiveRejected` | `null`（v1.4 没有结构化拒绝，现在也不凭空补一个） |
| `report.incomplete` | `true`（分类计数非 0） |
| `zip.failure` | `'over_limit'`，原值保留 |
| `zip.state` | `'ready'`，仍可重试 |

`archiveRejected` 为 `null` 而不是"根据 `failure: 'over_limit'` 猜一个 `kind`"——这是刻意的。v1.4 的记录里没有 `kind`、没有 `measured`、没有 `books`，猜出来的任何一个字段都是伪造。界面对这类老记录仍显示 v1.4 的文案（`zip.error`）+ 分类计数，信息量少于 v1.5 记录但仍完整可用。

### 2.3 v1.1 / v1.2 阅读计划

```ts
const legacy = emptyPlan(NOW);
addPlanItems(legacy, [{ bookKey: 'a', title: 'A', source: 'user' }], NOW);
const snapshot = { ...legacy, stats: undefined, statsComplete: undefined };   // v1.1 没有这两个字段
const restored = validatePlan(snapshot, NOW + 1);
```

| 断言 | 结果 |
| --- | --- |
| `restored.items` | 1 项，`bookKey === 'a'` |
| `restored.statsComplete` | `false`（"至少累计读完 0 本"是正确的下界） |
| `restored.stats.completed` | `0` |

v1.2 计划（有回填 `stats`、无 `statsComplete`）与 v1.5 计划（`statsComplete === true`）的对比：

```ts
const plan = emptyPlan(NOW);            // v1.5 的 emptyPlan 写显式 marker
addPlanItems(plan, […], NOW);
archiveItem(plan, plan.items[0].id, 'completed', NOW + 1);
const restored = validatePlan(plan, NOW + 2);
expect(restored.statsComplete).toBe(true);
expect(restored.stats.completed).toBe(1);
```

这两条是 v1.4 P2-6 的成果（`marker === true` 才判定完整），v1.5 未改。此处的价值是**回归位**：本轮的批量导入改动一旦误碰 `reading-plan.ts`，这两条会立刻变红。

## 3. 计数精度：250 本只留 100 名单

```ts
raw.rejected.overflow = { count: 250, names: Array.from({ length: 100 }, (_, i) => `书${i}.txt`) };
const report = batchReport(loaded[0]);
expect(report.overflow).toBe(250);                       // 数字精确
expect(report.rejectedNames.overflow).toHaveLength(100); // 名单是窗口
expect(report.overflow).toBeGreaterThan(BATCH_ITEM_LIMIT);
```

这条同时守两件事：`validateBatches` 不因为 `count > names.length` 报错（这是合法状态），以及报告层不把 `count` 降级成 `names.length`。

同一个策略在 `rejection.names` 上复用（`04` §8）。

## 4. 为什么"后缀字段"不会破坏老数据

`BatchZip.rejection` 是可选字段，`validateBatches()` 的写法是：

```ts
if (zip.rejection !== undefined) validateZipRejection(zip.rejection);
```

`undefined` 直接跳过。因此：

- 老数据加载 → 字段不存在 → 跳过校验 → 原样返回；
- 老数据再次保存 → JSON 序列化时可选字段不出现 → 文件内容与 v1.4 一致（除时间戳）；
- 一旦 v1.5 写入过 `rejection`，之后每次加载都会校验，且校验失败即整批拒绝加载（不静默丢弃）。

## 5. 回滚方向

反向兼容：v1.4 的代码读 v1.5 的批次会怎样？

- `validateBatches()`（v1.4）对未知字段不报错（JSON 里多一个 `rejection` 只是被忽略）；
- `batchReport()`（v1.4）不认识 `archiveRejected`，但它从 `rejected` 各桶算 `incomplete`，而 v1.5 的 count/entry 拒绝同时写了分类桶 → **v1.4 的报告仍能显示"超出单批 100 本 20 个"**；
- `bytes` / `disk` / `plan` 三种拒绝不写分类桶，v1.4 的报告会显示 `incomplete` 但计数为 0——信息量下降，但不会误报。

这是"回滚时降级而不错乱"的状态：不需要数据迁移，也不需要在回滚前清理记录。

## 6. 用例

| 用例 | 断言核心 |
| --- | --- |
| `adds no fabricated rejection counts`（v1.3） | `rejected` / `failure` / `rejection` 全为 `undefined`，`sha256` 不变 |
| `still reports the same refusals`（v1.4） | 2 / 1 / 3 三个计数与名单原样，`archiveRejected === null`，`failure` 保留 |
| `keeps a legacy queue migrating exactly as before`（v1.1） | `statsComplete === false`、`stats.completed === 0` |
| `counts a v1.5 plan as complete because the marker is explicit` | `statsComplete === true`、`stats.completed === 1` |
| `keeps the persisted overflow count exact past the name window` | `overflow === 250`、名单 100 项 |
