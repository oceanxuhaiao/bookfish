# 05 · UI 恢复与报告可见性（P2-4 / P2-5 / P2-6）

对应任务书第 4、5、6 节。这三项都是"用户能看到什么"的问题，合在一份文档里更便于交叉验证。

---

## 1. P2-4：报告在 preview 阶段就消失（真实 bug）

### v1.4 的代码

```ts
const report = view.report;
const refused = report.duplicate + report.unsupported + report.tooLarge + report.overBudget + report.overflow;
if (view.status !== 'preview' && (report.accepted || refused)) { … 渲染报告块 … }
```

### 三个叠加的漏洞

1. **`status !== 'preview'` 条件错**。拒绝恰恰大量发生在 preview 阶段：选文件夹时混进一张 `封面.jpg`、选了 101 个文件、ZIP 在 `preview` 状态下就被拒（解压失败但批次仍是 `preview`）。这些全部被这个条件挡掉。
2. **`state.error` 是瞬时的**。`fail()` 把原因写进一个内存字段，重启或重开面板就没了。
3. **持久化的报告又被隐藏**（第 1 点）。于是同一件事在两个地方都看不见——这是"用户永远不知道发生了什么"。

### v1.5 的代码

```ts
const refused = report.duplicate + report.unsupported + report.tooLarge + report.overBudget + report.overflow
  + (report.archiveRejected ? 1 : 0);
if (report.accepted || refused || report.failed || report.cancelled || report.needsReselect) { … }
```

只要下列任一为真就渲染：

| 触发 | 来源 |
| --- | --- |
| `accepted > 0` | 有书进批 |
| `duplicate > 0` | 重复或无效 |
| `unsupported > 0` | 格式不支持 |
| `tooLarge > 0` | 单本超 100 MiB |
| `overBudget > 0` | 超出本批 1 GiB 预算 |
| `overflow > 0` | 超出单批 100 本上限 |
| `archiveRejected !== null` | 整包拒绝 |
| `failed > 0` | 有失败条目 |
| `cancelled > 0` | 有已取消条目 |
| `needsReselect > 0` | 有待重新选择 |

不再看 `status`。一个纯 `preview` 的空批次（用户刚点开面板）不会渲染——`accepted` 为 0 且所有计数为 0，条件自然为假。

### 报告块的内容（≥10 项）

```
本次结果：进批 N 本 · 已入库 M 本 [· 等待 K] [· 失败 F] [· 已取消 C] [· 待重新选择 R]
未进入本批：重复或无效 X 个（甲.txt、乙.txt…）；格式不支持 Y 个（封面.jpg）；…
[整包未导入：<reason>]
[压缩包声明/解压后实测 N 本 / M 字节；本批可用 K 字节]
[没有发生部分导入（进批 A 本）；原始压缩包已保留。]
[涉及书目：…]
[下一步：<nextStep>]
这些文件仍在你的磁盘上，没有进入阅读计划；需要的话可以再选一次，只导入没进来的部分。
```

对照任务书第 4 节的 10 项要求：

| # | 要求 | 对应位置 |
| --- | --- | --- |
| 1 | 进批数 | `report.accepted` |
| 2 | 已入库数 | `report.shelfAdded` |
| 3 | 等待数 | `report.pending` |
| 4 | 失败数 | `report.failed` |
| 5 | 已取消数 | `report.cancelled` |
| 6 | 需重选数 | `report.needsReselect` |
| 7 | 全部拒绝分类精确计数 | 五行 `add(...)`，`count` 来自持久化的 `rejected` 各桶 |
| 8 | 可用文件名单 | 每个分类 `rejectedNames.<bucket>`，最多显示 3 个 + 省略号 |
| 9 | 原始 ZIP 保留情况 | `原始压缩包${archiveKept ? '已保留' : '未保留'}` |
| 10 | 下一步操作 | `下一步：${archive.nextStep}`（整包拒绝）/ 末尾"可以再选一次" |

### 整包拒绝的独立区块

整包拒绝不是"若干个文件被拒"，而是整个包。它的渲染刻意与分类行分开（`src/webui/batch-import.ts:474-500`），并且**区分实测与声明**：

- `measured: true` → "解压后实测 N 本 / M 字节"
- `measured: false` → "压缩包声明 N 本 / M 字节"

`books` / `totalBytes` 为 `null` 时显示"未知"，不显示 0（`04` §3）。

### 历史批次重开显示同样结果

因为 `report` 是 `batchReport(batch)` 的纯派生视图，而 `batch` 从磁盘读，所以"历史批次"与"当前批次"走同一条渲染路径。`tests/webui/batch-import-report.test.ts:120` 专门验证：

```ts
// 关闭面板 → 重开 → 报告仍在
expect(batch.textContent).toContain('格式不支持 1 个');
expect(batch.textContent).toContain('重复或无效 1 个');
```

## 2. P2-5：客户端过滤隐藏文件（真实缺陷）

### v1.4 的代码

```ts
const novels = picked.filter((file) => NOVEL.test(file.name));
const skipped = picked.filter((file) => !NOVEL.test(file.name)).map(relativeName);
if (!novels.length) throw new Error(say('这些文件都不是 .txt / .md / .epub / .pdf。', …));
…
const added = await ctx.invoke('import_batch_add', [batch.id, novels.map(...)]);
```

### 后果

| 情形 | 用户看到 | 实际发生 |
| --- | --- | --- |
| 文件夹里 10 本 txt + 3 张 jpg | 一句"3 个文件格式不支持，未导入" | 服务端从未收到那 3 个文件，`rejected.unsupported.count = 0` |
| 全部都是 jpg | 抛错"这些文件都不是…"，**批次都没创建** | 没有任何记录 |
| 关面板再开 | 那句话消失 | 没有任何地方能查到 |

第三条最严重：这不是"显示不够清楚"，是**拒绝从未发生**。任务书第 5 节的原话是"禁止仅前端显示一次就丢失"。

### v1.5 的代码

```ts
// 全量提交，服务端判定
const added = await ctx.invoke('import_batch_add', [batch.id, picked.map((file) => ({ name: relativeName(file), size: file.size }))]);
```

配套的两处调整：

1. **`NOVEL` 常量删除**（`src/webui/batch-import.ts:15` 的原 `const NOVEL = /\.(txt|md|epub|pdf)$/iu;`）。留着不用会误导后来者以为客户端还要过滤。
2. **上传循环改遍历 `picked`**，靠 `offered` map 判断哪些真的进批了：

```ts
for (const file of picked) {
  const itemId = offered.get(relativeName(file));
  if (!itemId) continue;   // 被服务端拒绝的文件没有 itemId，自然跳过
  …
}
```

`offered` 来自 `added.added`，只包含服务端接受的条目。所以遍历 `picked` 不会上传被拒文件，却也不需要提前过滤——**判定权只在服务端一处**。

### 提示文案改为指向报告

```ts
const refused = added.duplicates.length + added.unsupported.length + added.tooLarge.length
  + added.overBudget.length + added.overflow;
if (refused) {
  state.error = say(
    `本次有 ${refused} 个文件没有进入导入（${added.added.length} 个已接收），原因与文件名单见下方结果。`, …);
}
```

一行"看下方结果"，把用户引到持久化的报告块。不再在前端复述分类（那样就有两份可能不一致的文案）。

### 全不支持的文件夹

v1.4 会在这里 `throw`，批次都没创建。v1.5：批次照常创建，服务端返回 `added: []` + `unsupported: [所有文件]`，`rejected.unsupported.count` 持久化，报告块显示"格式不支持 N 个"。历史列表里也留下一条 `total: 0` 的记录。

`tests/webui/batch-import-report.test.ts:153`：

```ts
// 全是 jpg 的文件夹
expect(batch.textContent).toContain('格式不支持 2 个');
const summaries = await invoke('import_batch_status', []);
expect(summaries).toHaveLength(1);      // 记录存在，不是"什么都没发生"
expect(summaries[0].total).toBe(0);
```

### 计数 / 名单 / 批次更新的一致性

单一来源：`library.addImportBatchItems()` → `addBatchItems()` → `classifyInputs()` → `recordRejected()` 在同一次原子写里完成。前端只读 `added` 的返回值做一句提示，真正的计数与名单全部来自持久化的 `rejected`。因此不存在"前端说 3 个、后端记 0 个"的可能。

## 3. P2-6：首次 ZIP 失败后的死路

### v1.4 的代码

```ts
function fail(error: unknown): void {
  state.busy = null;
  state.error = String((error as Error).message ?? error);
  render();
}
```

### 死路是怎么形成的

首次 ZIP 上传的时间顺序：

```
import_batch_create        → 服务端已写入批次记录（含 zip 记录）
zipBegin + 分块上传        → source.zip 落盘、SHA-256 已校验
zipFinish                  → 解压失败，rejection 已持久化，抛 ZipStateError
                           ↑ 此刻前端 state.view 仍是 null（从未 status 过）
                           ↑ state.summaries 是创建前取的（不含这个批次）
fail()                     → 只写一句 state.error，render()
```

用户看到：一个错误文字，没有批次卡片、没有"重试解压"按钮、历史列表里也没有这个批次。**唯一出路是关闭面板重开**（甚至重启宿主），因为它才会重新 `import_batch_status([])`。

### v1.5 的代码

```ts
function fail(error: unknown): void {
  const original = String((error as Error)?.message ?? error);
  const hadBatch = state.batch !== null;
  state.busy = null;
  state.error = original;
  render();                           // 先把原始错误显示出来，不等刷新
  if (!hadBatch) return;              // create() 失败时无记录可读，不必刷新
  void (async () => {
    try {
      if (state.batch?.id) {
        state.view = await ctx.invoke<ImportBatchView>('import_batch_status', [state.batch.id]);
        state.batch = { ...state.batch, status: state.view.status };
      }
      state.summaries = await ctx.invoke<ImportBatchSummary[]>('import_batch_status', []);
    } catch (refreshError) {
      // 刷新失败不能覆盖原始错误：用户两个都需要
      state.error = `${original}\n（刷新批次状态失败：${String((refreshError as Error)?.message ?? refreshError)}）`;
    }
    render();
  })();
}
```

### 四条设计决策

| 决策 | 理由 |
| --- | --- |
| **先 `render()` 再刷新** | 刷新是网络/磁盘往返，用户不该等它才看到失败原因 |
| **`hadBatch` 判断** | `import_batch_create` 本身失败时没有记录可读，无谓的刷新会再抛一次错 |
| **`void (async () => …)()`** | `fail()` 的调用点是 `.catch(fail)`，签名必须是同步的；刷新在后台跑，完成后自己 `render()` |
| **刷新失败拼接而非替换** | 原始错误是根因，刷新失败是次生。合成一条会丢掉用户最需要的信息 |

### 恢复后的可见内容

刷新后 `state.view` 有值 → 渲染完整批次卡片（`zip.name`、`zip.size`、`zip.state`、`zip.failure`、`rejection` 区块）+ 报告块 + 可操作按钮。`rejection.nextStep` 告诉用户"拆包"，`state: 'ready'` 让"重试解压"按钮出现。

`tests/webui/batch-import-report.test.ts:173`：

```ts
attach(picker(root, 'zip'), [new File([brokenZip], 'broken.zip')]);
await waitFor(() => … batch.textContent 不再含 '正在读取压缩包');
expect(batch.textContent).toContain('broken.zip');
const summaries = await invoke('import_batch_status', []);
expect(summaries).toHaveLength(1);                            // 历史列表已刷新
expect(status.zip?.state).toBe('ready');
expect(status.zip?.failure).toBe('transient');
expect(status.zip?.reselectable).toBe(false);
expect(batch.textContent).toContain('重试解压');              // 恢复按钮在
```

### 已成功的 ZIP 失败不回归

v1.4 的好行为（已有批次失败后保留恢复路径）没有被改动：`refuseArchive()` 只加字段、`fail()` 只加字段，`state` 始终 `ready`。`tests/webui/batch-import-report.test.ts:209` 验证 120 本 ZIP 在首次上传时被拒后，面板不用重开就显示 `超过单批`、`拆`、`too-many.zip`、`压缩包已保留`。

## 4. 三个改动的交互

P2-4 / P2-5 / P2-6 不是三个独立补丁，它们共同组成一条链：

```
P2-5  服务端收到全部文件  →  拒绝有记录、有计数、有名单
P2-3  拒绝被结构化持久化  →  记录能存活重启
P2-4  报告在任何状态渲染  →  记录能被看到
P2-6  失败后自动重读状态  →  看到的是刷新后的真实状态，不是过期快照
```

任何一环缺失，另外三个的价值都会打折。这也是为什么它们在同一轮完成。

## 5. 用例汇总（5 例）

| 用例 | 验证 |
| --- | --- |
| `shows the report for a folder pick containing an unsupported file, before starting` | preview 阶段就可见（`格式不支持 1 个`、`封面.jpg`、`共 3 本`） |
| `keeps the report after closing and reopening the panel` | 持久化 + 历史重开（`格式不支持 1 个`、`重复或无效 1 个`） |
| `records a batch that contains only unsupported files instead of failing silently` | 全不支持文件夹（`格式不支持 2 个`、历史 1 条、`total: 0`） |
| `recovers the view when the very first ZIP upload fails to extract` | 首次失败恢复（`ready` / `transient` / `重试解压` / 历史已刷新） |
| `shows the over-limit archive it refused without needing a reopen` | 首次拒包（`超过单批` / `拆` / `too-many.zip` / `压缩包已保留` / `kind: 'count'` / `books: 120`） |
