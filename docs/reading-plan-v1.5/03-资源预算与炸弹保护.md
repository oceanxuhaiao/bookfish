# 03 · 资源预算与解压炸弹保护（P1-2）

对应任务书第 2 节。命题：**新增的第二道内容检查不能成为新的资源漏洞。**

---

## 1. 预算常量：一个字都没改

```ts
export const DEFAULT_BATCH_BUDGET: BatchBudget = {
  batchBytes: BATCH_STAGING_BYTES,                            // 1 GiB
  fileBytes: MAX_BATCH_FILE_BYTES,                            // 100 MiB
  zipBytes: ZIP_MAX_BYTES,                                    // 512 MiB
  workspaceBytes: ZIP_MAX_BYTES + BATCH_STAGING_BYTES,        // 1.5 GiB
};
```

对照 v1.4 的 `src/import-batches.ts`：这四行的数值、公式、以及构造函数里的自检

```ts
if (this.budget.workspaceBytes < this.budget.zipBytes + this.budget.batchBytes)
  throw new Error('Batch workspace budget must cover the archive plus the staged books');
```

全部原样保留。`workspaceBytes` 之所以是 `zipBytes + batchBytes` 而不是 2.5 GiB：归档与解压树只是**短暂共存**，随后每条是 `rename`（元数据操作，不复制字节），所以真实峰值就是这两项之和，不存在第三份副本。

## 2. 三层闸门，一层都没少

| 层 | 位置 | 成本 | 拦住什么 |
| --- | --- | --- | --- |
| 磁盘预检 | `ceiling < 1` 与 `free < estimate` | 一次 `dirTreeBytes` + 一次 `statfsSync` | 本批已无空间、磁盘物理不足 |
| 索引预检 | 三道 `plan` 判定 | 一次 ≤8 MiB 有界读 | 可读索引已知的 count / entry / bytes 超限 |
| Worker 上限 | `extractRuntimeZip(..., limits)` | 解压本身 | 索引读不到时的 count / entry / bytes 超限 |

`ceiling` 的公式未变：

```ts
const existing = Math.max(0, dirTreeBytes(this.batchDir(batchId)) - zipSize);
const ceiling = Math.min(this.budget.batchBytes - existing,
                         this.budget.workspaceBytes - zipSize - existing);
```

`existing` 扣掉归档自身，所以重试场景（已有一部分 `.src`）不会被重复计入；`Math.max(0, …)` 保证目录比声明还小的异常不会变成负数。

## 3. Worker 上限：原样传入实际预算

```ts
const outcome = await extractRuntimeZip(zipPath, target, signal, undefined, {
  maxEntries: BATCH_ITEM_LIMIT * 4,          // 400
  maxTotalBytes: ceiling,                    // 本批真实可用字节
  maxEntryBytes: this.budget.fileBytes,      // 100 MiB
});
```

Worker 的默认值（`src/novel-runtime/zip-worker.ts:24`）是 `maxEntries: 12_000` / `maxTotalBytes: 1_200 MiB` / `maxEntryBytes: 512 MiB`；这里**显式收紧**成批次预算，不是放宽。三处均未修改。

Worker 的 12 条拒绝规则（不可放宽，v1.5 一字未改）：

| 码 | 规则 | 行 |
| --- | --- | --- |
| `zip_invalid` | 无法打开 / 读取失败 | 75、76 |
| `zip_encrypted` | `generalPurposeBitFlag & 0x1` | 80 |
| `zip_compression` | 压缩方法不是 0（store）或 8（deflate） | 81 |
| `zip_entry_name` | `safeName()` 失败（穿越 / 绝对路径 / 设备名） | 83 |
| `zip_duplicate` | `name.toLowerCase()` 重复 | 87 |
| `zip_too_many_entries` | 条目数 > `maxEntries` | 90 |
| `zip_symlink` | mode 高 4 位 = `0xa000` | 93 |
| `zip_entry_type` | 特殊文件 / 目录带数据 | 94、96 |
| `zip_entry_too_large` | `uncompressedSize > maxEntryBytes` | 101 |
| `zip_bomb` | `> 1 MiB` 且压缩比 > 220 | 102 |
| `zip_too_large` | 累计 `totalBytes > maxTotalBytes` | 106 |
| `zip_traversal` | `resolve()` 后不在 `destRoot` 之下 | 108 |
| `zip_write` / `zip_read` / `zip_size` | 写入 / 读取 / 大小不符 | 111-131 |

## 4. "不允许先写入超额文件再检查"——结构上的保证

Worker 在写任何字节之前就按**声明大小**判定：

```ts
if (entry.uncompressedSize > limits.maxEntryBytes) return abort('zip_entry_too_large', …);   // 第 101 行
totalBytes += entry.uncompressedSize;
if (totalBytes > limits.maxTotalBytes) return abort('zip_too_large', …);                     // 第 106 行
```

判在第 101/106 行，第一次 `openSync(target, 'wx')` 在第 111 行。所以"先写 1.2 GiB 再发现超 1 GiB"在结构上不可能发生。这一点是 v1.3 就有的性质，v1.5 的第二道检查没有改动它——**新增的检查跑在解压完成之后，而解压本身已经被 Worker 的声明上限约束住了**，因此新检查不会让任何额外字节落盘。

同时在流式写入中还有一道实测保护（第 119 行）：`written > entry.uncompressedSize` 立刻 `abort('zip_size')`，防止声明小、实际大的条目。

## 5. 独立临时目录：第二道检查的隔离前提

```ts
const target = join(dir, randomUUID() + '.extract');
mkdirSync(dir, { recursive: true });
```

- 目录名带随机 UUID，不与 `.src` 暂存位同名，不与任何已知批次条目同名；
- 解压产物落在 `.extract/` 里，**确认前不进入 `.src`**；
- 成功路径：逐条 `renameSync(join(target, …), stagedPath)` —— 同目录树、同文件系统，元数据操作；
- 失败路径（`catch` 首句）：`rmSync(target, { recursive: true, force: true })`；
- 成功路径结尾：`rmSync(target, { recursive: true, force: true })`；
- 两条路径都有，所以 `.extract` 不可能泄漏。`tests/import-batch-zip-unknown.test.ts` 与 `budget-integrity` 都在每个拒绝用例后断言 `extractDirs(batchId)` 为空。

`cleanStale()` 在启动时还会扫掉上次运行遗留的目录（只认已知批次 ID 与本模块自己的 `.src` / `.extract` 命名形状）。

## 6. 未知格式不会被误算成"可导入小说"

第二道检查的输入是**真实解压出的文件清单**，但清单本身经过与上传路径同一个分类器：

```ts
const verdict = classifyInputs(
  entries.map((entry) => ({ id: 'pending', name: entry.path, size: entry.size, title: entry.path,
    sourceSha256: entry.sha256 })),
  { seen, itemCount: acceptedBefore, declaredBytes, itemLimit: BATCH_ITEM_LIMIT,
    fileBytes: this.budget.fileBytes, batchBytes: this.budget.batchBytes });
```

`classifyInputs` 的第三条判定就是 `isSupportedNovel(name)`（`/\.(txt|md|epub|pdf)$/iu`），不支持格式进 `unsupported` 桶，不占 `itemLimit` 名额，也不占 `declared` 字节。所以：

- 一个 300 张 jpg + 50 本 txt 的归档 → 判 50 本，不拒绝；
- 一个 300 本 txt + 50 张 jpg 的归档 → 判 300 本，整包拒绝；
- `__MACOSX/` / `.DS_Store` 在进入分类器之前就被过滤（`entry.path.split('/').some(p => p.startsWith('.'))`），即使 `.DS_Store` 的名字恰好叫 `.txt` 也不算。

`tests/import-batch-zip-count-rules.test.ts:94` 用 8 个条目（3 支持 + 2 不支持 + 1 `__MACOSX` + 1 `.DS_Store` + 1 支持）验证：最终 `items` 恰好 4 本、`report.unsupported === 2`。

## 7. 部分失败后原 ZIP 可重试

`refuseArchive()` 不改 `zip.state`，因此保持 `ready`；`fail()` 同样保持 `ready`（v1.4 的语义，v1.5 未改）。`ready` 是"归档已验证且仍在磁盘上"的状态标记，而"能否真的重试"由 `failure` 决定：

| `failure` | 重试方式 |
| --- | --- |
| `over_limit` | 用户拆包后重新选包（`zipReselect` prepare → begin） |
| `disk` | 释放空间后点"重试解压"，归档不动 |
| `transient` | 点"重试解压"，归档不动 |
| `missing` / `unverifiable` | 只能重选（归档不在或身份无法证明） |

`resume()` 对所有 `ready` 且 `failure` 允许的批次重试一次，但**跳过 `over_limit`**：那是确定性结论，重启不会改变它。

## 8. 峰值实测（不是估算）

```ts
const peak = dirTreeBytes(this.batchDir(batchId));
if (peak > this.workspaceBytes) throw new Error('Archive would peak beyond the batch workspace budget');
this.library.updateImportBatch(batchId, (draft) => {
  if (!draft.zip) return;
  draft.zip.peakBytes = Math.max(draft.zip.peakBytes ?? 0, peak);
});
```

`peak` 是"归档 + 解压树"同时在盘上那一刻的**真实递归字节数**，不是"归档大小 × 2"的估算。`Math.max` 会跨重试保留历史最大峰值，供审核与后续调参。`dirTreeBytes()` 不跟随符号链接、目录本身不计、读不到的目录抛错（"未知"不得报成 0）。

## 9. 第二道检查的成本上界

| 项 | 上界 | 依据 |
| --- | --- | --- |
| 额外磁盘 | ≤ `ceiling`（本批真实可用字节） | Worker `maxTotalBytes: ceiling` |
| 额外内存 | O(条目数 × 路径长度) | `outcome.files` 是元数据数组；文件内容从不整体读入（流式 `writeSync`） |
| 额外时间 | 一次完整解压 + 一次 SHA-256 | 归档已在上传时哈希过一次，解压时 Worker 逐条再算（`hash.update(chunk)`） |
| 额外条目 | ≤ 400 | `maxEntries: BATCH_ITEM_LIMIT * 4` |

`maxEntries: 400` 是刻意与 `100` 分离的：一个 150 本的包需要能写出来才能"实测到 150 本"并给出准确数字；如果卡在 100，就只能得到 `zip_too_many_entries` + `books: null`，用户看不到"到底多少本"。400 的上界保证最坏情况仍是有界的（400 个文件 + 目录）。

## 10. 一处注意：`ceiling` 与 `estimate` 的分工

```ts
const estimate = plan ? plan.totalUncompressed : ceiling;
const free = this.diskFree(this.batchDir(batchId));
if (free === null) throw this.fail(batchId, 'disk', '无法测量磁盘剩余空间…');
if (free < estimate) throw this.fail(batchId, 'disk', `磁盘剩余 ${free} 字节，本次解压约需 ${estimate} 字节…`);
```

`estimate` 用**归档自己的声明**，不用最坏值——否则一个 2 MB 的包会要求 1 GiB 剩余空间（v1.3 已修正的行为，v1.5 保留）。索引读不到时 `estimate = ceiling`，退回最坏值，且 `diskFree === null` 仍然拒绝：**无法测量磁盘不得当作"空间充足"**（`tests/import-batch-zip-budget-integrity.test.ts:121`）。
