## P2-1 ZIP 上传完整性与恢复（任务书第 3 节）

### 声明大小与内容校验

| 接口 | 校验 |
| --- | --- |
| `zipBegin()` | 批次必须是 `source === 'zip'` 且 `status === 'preview'`；持久化 `name`、声明 `size`（1 byte–512 MiB）、`claimedSha256`（仅作期望值）、批次与上传身份；重开时保留上次已接受的 `sha256` 与声明大小 |
| `zipChunk()` | 状态必须为 `uploading`；offset 为非负整数；分片 ≤ `BATCH_CHUNK`；`offset + len` **不得超过本批次声明的 size**；offset 必须连续；重复分片仅在字节完全一致时幂等接受；base64 严格回编码校验 |
| `zipFinish()` | 实际长度必须等于声明 size；服务端流式计算完整 SHA-256；与 `claimedSha256`（若有）、与上次已接受的 `sha256`（若有）逐一比对；全部通过才写 `sha256` 并置 `ready`，然后进入解压 |

关键设计：**声明大小是天花板，不是全局最大值**。声明 1 MB 却上传 2 MB 会被 `offset + len > zip.size` 拒绝；声明 1 MB 只传 500 KB 会被 `actual !== zip.size` 拒绝完成。

### 四态状态机与恢复入口

```
uploading ──(重启 resume)──► needs_reselect ──(zipReselect)──► uploading
    │                                                            │
    └──(zipFinish 校验通过)──► ready ──(importZip 成功)──► extracted
                                   │
                                   └──(解压失败)──► needs_reselect（保留 ZIP 供重试）
```

- `resume()`：半截上传（`uploading`）→ 删除半截文件、置 `needs_reselect`、计入 `archives`；完好但未解压（`ready` 且文件在）→ 直接重试 `importZip()`，同样计入 `archives`。
- `zipReselect()`：复用原 `batchId`、声明 `size`、已接受的 `sha256`，清空文件让 offset 从 0 重新连续；若批次已有条目或已 `extracted` 则拒绝，避免把不同书塞进旧批次历史。
- `src/world.ts` 新增 `import_batch_zip_reselect` 分发入口；`status(batchId)` 暴露 `zip?: BatchZipView`（含 `state`、`sha256`、`peakBytes`），面板据此显示"等待重新选择 / 正在重新上传 / 待解压 / 已解压"与峰值。
- 无法安全恢复时（无摘要、已有条目、已解压），明确提示并允许取消旧批次，不留下无操作入口的预览批次。

### 验收逐条（任务书 3.3）

| 验收项 | 判定 | 用例 |
| --- | --- | --- |
| 声明 1 MB 但上传 2 MB，拒绝 | ✅ | `refuses a body longer than the declared size`；`import-batch-chunks`「refuses a chunk that runs past the declared size」 |
| 声明 1 MB 只传 500 KB，拒绝完成 | ✅ | `refuses to finish a truncated archive` |
| 中断后重启出现重新选择入口 | ✅ | `reports an interrupted archive upload after a restart and can reopen the same batch` |
| 同大小但不同 SHA-256 的 ZIP 拒绝 | ✅ | `refuses a re-uploaded archive of the same length but different content`、`refuses an archive whose content does not match the claimed digest` |
| 同一 ZIP 恢复后不重复导入已成功书籍 | ✅ | `persists the verified digest and keeps the archive when extraction fails`、`never deletes an archive that has not been extracted yet`；`import-batch-zip-peak`「can retry the extraction from the stored archive after a restart」 |

## P2-2 修复当前阅读状态展示（任务书第 4 节）

### 问题

`planView.current` 只从计划条目里找 `active`。用户正在读一本不在计划里的书（升级后未加入、或被移出但继续读）时，计划页显示"没有正在阅读的书"。

### 实现

- `planView()` 新增 `reading` 字段：由 `LibraryState.selected` 派生，带 `bookKey / title / author / progress / progressUnit / chapter / complete / inPlan`。`current` 保持原义（计划内的 active 条目），两者并存。
- `inPlan` 用 `items.some(...)` 判断；不计入 `total`，不影响 `next`。
- 计划页：空态条件从 `!plan.total && !plan.completedCount` 改为 `!plan.total && !plan.reading`；`reading` 存在时展示"正在读"卡片，计划外显示 `计划外 · 已读 N%` 徽标、真实进度单位、章节名，并提供"把这本书加进计划"按钮。
- `reading.inPlan === false` 时明确说明"不计入计划本数，也不会挤掉计划里的下一本"。
- 若计划内 active 存在但 `selected` 为空，仍展示该条目并说明"排到了但还没被选中阅读"，不伪造进度。

### 验收逐条（任务书第 4 节）

| 场景 | 判定 | 用例（`tests/plan-display.test.ts`） |
| --- | --- | --- |
| 旧版本升级后当前书未进入计划 | ✅ | `reports the current book after an upgrade that never planned it` |
| 用户移出计划但继续阅读 | ✅ | `keeps a removed-but-still-read book in the reading slot` |
| 当前书加入计划 | ✅ | `marks the current book as planned when it is in the playlist` |
| 当前书完读但没有下一本 | ✅ | `still shows a finished current book that has no successor` |
| 当前书不在计划且计划为空 | ✅ | `keeps the current book visible when the plan is empty`、`reports a current book that was never added to the plan` |

补充：`drops to no reading book when nothing is selected`。

## P2-3 补齐 keepReading 操作及错误提示（任务书第 5 节）

### 实现

1. `Library.updatePlanAction()` 把 `keepReading === true` 安全透传给 `removeFromPlan()`（v1.1 漏传，导致该能力在 UI 上不可用）。
2. 计划页把两个承诺分开成两个按钮：
   - **「停止读这本，改读下一本」** → `{ action:'remove', status:'skipped', stop:true }`
   - **「移出计划，继续读这本」** → `{ action:'remove', status:'removed', keepReading:true }`
3. 两者都保留正文、进度、手账、读后感；停止操作带二次确认。
4. **没有可读的下一本时 stop 按钮直接禁用**，并在下方解释"没有其他可读的下一本，所以不能'换下一本'；只想让它离开计划但仍继续读，用下面的按钮"。暂缓（`notBefore`）条目不计入可读下一本，不会被绕过。
5. 页面顶部新增 `.plan-error` 错误条；`act()` 不再 `catch(() => undefined)`，排序失败、系列操作失败、持久化失败都展示服务端错误信息；每次点击先清空旧错误。

### 验收逐条（任务书第 5 节）

| 验收项 | 判定 | 证据 |
| --- | --- | --- |
| 当前书继续阅读但移出计划 | ✅ | `tests/webui/plan-panel.test.ts`（keepReading 用例）+ `plan-display`「keeps a removed-but-still-read book in the reading slot」 |
| 当前书停止并切换下一本 | ✅ | `plan-panel` stop 用例（v1.1 已有，本轮保持） |
| 没有下一本时安全拒绝 | ✅ | `plan-panel` 用例断言按钮 disabled + 解释文案 |
| 暂缓书籍不被绕过 | ✅ | 可读下一本的计算过滤 `notBefore > Date.now()` |
| 用户暂停时不产生意外阅读推进 | ✅ | 本轮不改调度；`plan-combination` / `plan-advance` 既有用例继续通过 |
| 每种拒绝都有明确反馈 | ✅ | `.plan-error` 错误条用例；`act()` 统一上报 |

## P2-4 阅读计划历史保留策略（任务书第 6 节）

### 问题

`PLAN_ARCHIVE_LIMIT = 300`，`archiveItem()` 直接 `slice(-300)` 丢旧记录；`completedCount` 直接从 archive 计算，老用户读到第 301 本时"累计完成"会下降。系列全部归档后 `dropUnusedSeries()` 会删掉系列，历史里只剩无法解析的 `seriesId`。

### 实现（不扩大 `library.json`）

- 新增 `PlanStats { completed, skipped, removed, truncated, lastArchivedAt? }`，作为累计计数的唯一真相；`emptyPlan()` 初始化。
- `archiveItem()`：窗口仍按 300 条裁剪，但每次裁剪把溢出行数累加到 `truncated`，并按状态累加 `completed / skipped / removed`，写 `lastArchivedAt`。**计数不随窗口收缩**。
- `migrateLegacyQueue()`：迁移进来的 done / cancelled 行同样计入累计计数。
- `validateStats()`：旧计划缺 `stats` 时从现存 archive 回填（可用的下界）；若持久化计数小于其自身归档行数则**拒绝加载**而不是信任错误数据。
- `dropUnusedSeries()`：删组前把组名写进归档条目的 `seriesName`，并把 `seriesId` 置 `null`；历史保留可读名称，不留悬空引用。仍被等待条目使用的组保留。
- `planView()` 暴露：`completedCount`（累计）、`completedKept`（窗口内）、`skippedCount`、`removedCount`、`truncatedCount`、`archiveLimit`（300）、`archiveKept`；`archive` 视图仍只返回最近 50 条。
- 计划页新增历史说明：`历史只保留最近 300 条（当前 N 条）… 更早的 X 条已不再列出，但累计数量仍然计入；跳过 Y 本、移出 Z 本。` 摘要从"已完成"改为"累计读完"，避免误导。

### 验收逐条（任务书第 8 节点名项）

| 验收项 | 判定 | 用例（`tests/plan-history.test.ts`） |
| --- | --- | --- |
| 归档 300 条上限及累计统计 | ✅ | `counts every archived book even when the window is full` |
| 累计跳过 / 移除可区分 | ✅ | `keeps skipped and removed apart from finished` |
| 截断有可审计信息 | ✅ | 同上 + `truncatedCount` 断言；`rejects counters that are smaller than the archive they claim to describe` |
| 旧计划回填 | ✅ | `backfills counters for a plan written before they existed` |
| 迁移行计入 | ✅ | `counts migrated legacy rows instead of dropping them from the totals` |
| 系列归档后的历史引用 | ✅ | `keeps the series name and clears the dangling id when the group is dropped`、`keeps a group that still has a waiting member` |

### 明确声明

本架构**不保留完整逐本明细**：`library.json` 只保留最近 300 条归档（UI 返回最近 50 条），超出部分只留下累计计数与 `truncated`。这不是"全部阅读历史"，页面已明示。完整导出的后续方案见 `04-数据结构与历史保留说明.md`，**本轮未实施、未接入新存储系统**。
