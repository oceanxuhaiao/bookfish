# 04 · 数据结构与历史保留说明

## 1. 持久化布局：本轮未改

| 项 | v1.1 | v1.2 |
| --- | --- | --- |
| 文件布局 schema | 8 | **8（未改）** |
| `LibraryState` schema | 4 | **4（未改）** |
| 写入口 | 仅 `Library.change()` 单快照 | 同左 |
| 新增持久化字段 | — | `ReadingPlan.stats`、`PlanArchiveEntry.seriesName`、`BatchItem.sourceSha256/sourceName`、`ImportBatch.zip` |

**关键**：v1.1 把文件布局提升到 8 是为了降级 fail-closed；本轮**不碰布局版本**，因此不引入新的降级风险。所有新字段都在各自 `validate*` 函数里做兼容读取：

- `validatePlan()` → `validateStats(raw, archive)`：`stats` 缺失时从现存 archive 回填（可用的下界），不会让旧库打不开。
- `validateBatches()` → `zip` / `sourceSha256` / `sourceName` 都是可选字段，旧批次原样读取；`digestOf()` 保证一旦存在就必须是合法小写 64 位 hex。
- `BookStorage.hydrate()` 的 `8 → state 4` 映射不变；v0.66.7 读到布局 8 仍然拒绝打开（v1.1 的 `schema-downgrade` 7 例继续通过）。

## 2. 新增/扩展的数据结构

```ts
interface PlanStats {
  completed: number;      // 累计读完（不随归档窗口收缩）
  skipped: number;        // 累计跳过 / 停止
  removed: number;        // 累计移出
  truncated: number;      // 因窗口上限被移出明细的历史行数（审计用）
  lastArchivedAt?: number;
}

interface PlanArchiveEntry {
  // ...v1.1 字段
  seriesId: string | null;
  seriesName?: string;    // 系列被解散后仍可读的名字
}

interface BatchItem {
  // ...v1.1 字段
  sourceSha256?: string;  // 服务端计算的内容身份
  sourceName?: string;    // 选择器报告的原始相对路径
}

interface BatchZip {
  name: string; size: number;
  sha256?: string; claimedSha256?: string;
  state: 'uploading' | 'needs_reselect' | 'ready' | 'extracted';
  peakBytes?: number;
}
```

`ImportBatch.zip?: BatchZip` 仅 `source === 'zip'` 时存在。

## 3. 历史保留策略（明确声明）

| 问题 | 答案 |
| --- | --- |
| 明细保留多少？ | **最近 300 条**（`PLAN_ARCHIVE_LIMIT`）。计划页视图再取最近 50 条展示。 |
| `library.json` 会无限增长吗？ | 不会。窗口有界，本轮**没有**扩大它，也没有接入新存储系统。 |
| 累计统计会失真吗？ | 不会。`plan.stats` 独立保存 completed / skipped / removed，裁剪只影响明细窗口。 |
| 被裁掉的旧记录去哪了？ | 明细不可恢复；但 `truncated` 记录被裁行数，`lastArchivedAt` 记录最后一次归档时间，累计计数仍然完整。 |
| 用户会不会误以为 300 条就是全部？ | 页面明确写出"历史只保留最近 300 条（当前 N 条）… 更早的 X 条已不再列出，但累计数量仍然计入"，摘要用"累计读完"而非"已完成"。 |
| 系列解散后历史还能读吗？ | 能。`dropUnusedSeries()` 把组名写进 `seriesName`、`seriesId` 置 `null`，不留悬空引用。 |

**这不等于完整逐本阅读历史。** 本轮按任务书第 6 节"保留现有有界数据结构，不要无条件扩大 library.json"执行，只做到：累计计数独立、分类可区分、截断可审计、策略可见、系列引用不留垃圾。

## 4. 一致性规则

- `validateStats()` 拒绝"累计计数小于其自身归档行数"的快照（防手工篡改或损坏数据被当成真相）。
- `archiveItem()` 一次 `Library.change()` 内完成：追加归档 → 裁剪窗口并累加 `truncated` → 按状态累加分类计数 → 写 `lastArchivedAt` → `dropUnusedSeries()` → `touch()`。计数与明细在同一次提交里，不会出现"明细在、计数丢"。
- `migrateLegacyQueue()` 把旧队列的 done / cancelled 行同样计入累计计数。
- `planView.completedCount` 现在取 `plan.stats.completed`（累计），另给 `completedKept`（窗口内实际行数）、`skippedCount`、`removedCount`、`truncatedCount`、`archiveLimit`、`archiveKept`，前端可区分"累计"与"最近保留"。

## 5. 后续完整导出方案（本轮不实施）

若产品决定要完整逐本历史，建议按以下顺序评估，**不在本阶段授权范围内**：

1. 在 `Library` 增加只读导出接口，把 `plan.stats` + 现存 300 条明细导出为 JSON/CSV，供用户自行归档；成本最低，不改变持久化。
2. 若需长期可查询历史，采用 append-only 的独立历史文件（按年/月分片），由 `Library.change()` 之外的专用写入口维护；需单独评估崩溃一致性与备份策略。
3. 任何方案都必须回答：与 `library.json` 单快照的一致性、降级时旧版本的行为、以及导出是否算"新存储系统"（任务书第 6 节禁止本轮接入）。

## 6. 降级与回滚

本轮不改布局，故 v1.1 的降级结论继续有效：布局 8 使 v0.66.7 在 `validateState` 抛错并拒绝打开库，避免旧版本静默丢弃计划/批次数据。代价仍是"降级期间库不可用"，回滚前须用新版本导出备份。新增字段对旧版本不可见，但因为布局 8 已整体拒绝打开，不存在"旧版本读到新字段后覆盖"的路径。
