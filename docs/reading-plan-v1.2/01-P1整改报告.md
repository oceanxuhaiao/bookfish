## P1-1 重新选择文件必须验证内容身份

### 1.1 问题

v1.1 的 `ImportBatches.reselect()` 只比较文件大小。两个同大小、不同内容的文件会被当成同一本，重新上传后进入原 `itemId` 对应的书目身份下，正文与阅读进度静默错配。前端传入的摘要如果直接采信，同样可以被绕过。

### 1.2 实现

| 位置 | 改动 |
| --- | --- |
| `src/import-batch.ts` | `BatchItem` / `BatchItemInput` 增加 `sourceSha256?`、`sourceName?`；新增 `digestOf()` 只接受小写 64 位 hex；`addBatchItems()` 校验并持久化；`validateBatches()` 对落盘值做同样校验 |
| `src/import-batches.ts` | 新增 `sha256File()`：256 KiB 缓冲区 + `readSync` 流式哈希，**不把整个文件读进内存** |
| `src/import-batches.ts:252` | `stage()` 在最后一片落盘完成后，服务端计算暂存文件摘要并写入 `sourceSha256` |
| `src/import-batches.ts:282` | `reselect()` 依次校验：状态为 `needs_reselect`、大小一致、文件名 / 原始相对路径一致、重新计算的 SHA-256 与持久化摘要一致；任一项不符即拒绝 |
| `src/import-batches.ts:684` | `launch()` 在把暂存文件交给 `ImportJob` **之前**再算一次摘要比对，绕过面板直接改文件同样会被拦下 |
| `src/webui/batch-import.ts` | `fileDigest()` 仅对 ≤64 MiB 的前端文件计算"期望摘要"；它只是 `claimedSha256`，**服务端从不信任** |
| `src/import-batches.ts` | ZIP 档案的 `claimedSha256` 不匹配时 `zipFinish()` 会清除该错误声明，避免把批次永久锁死 |

**旧批次没有可信摘要时不假装验证**：`reselect()` 明确抛错要求新建批次并重新导入，原条目的状态、错误与证据全部保留，不覆盖。对应 `import-batch-identity`「refuses to guess for an entry that never recorded a digest」。

### 1.3 验收逐条（任务书 1.3）

| 验收项 | 判定 | 用例 |
| --- | --- | --- |
| 同大小不同内容的文件拒绝 | ✅ | `refuses a same-size file with different content` |
| 同名不同内容的文件拒绝 | ✅ | 同上 + `refuses a different file name before any byte is uploaded` |
| 同内容文件允许恢复 | ✅ | `accepts the original file again and keeps the item id and the order` |
| 上传中途失败可以再次恢复 | ✅ | `lets a failed re-upload be attempted again` |
| 恢复后 itemId 和顺序不变 | ✅ | 同上；`import-batch-chunks`「re-upload after reselect restores the same item instead of creating a new one」 |
| 错误文件不得进入 ImportJob | ✅ | `re-checks the bytes right before the parser runs` |

补充覆盖：`records the digest of the accepted upload`、`hashes files in bounded memory`（内存上界）、`refuses a body longer than the declared size`。

### 1.4 内存与并发

摘要计算固定 256 KiB 缓冲区，与文件大小无关；单批次仍受 `BATCH_CONCURRENCY = 2` 限制，不会因哈希放大并发或内存。`hashes files in bounded memory` 用例以大文件 + 小堆验证该性质。

## P1-2 重新核算 ZIP 的真实磁盘峰值

### 2.1 问题

v1.1 的 1 GiB 限制只约束"声明的书籍文件总量"。实际上 ZIP 原件、解压临时目录、以及把解压文件**复制**成 `.src` 暂存文件可能同时存在，最坏会到 `512 MiB ZIP + 1 GiB 解压树 + 1 GiB 副本 ≈ 2.5 GiB`。声明上限与真实峰值不一致。

### 2.2 完整资源核算

| 资源 | 是否计入 | 处理方式 |
| --- | --- | --- |
| 原始 ZIP（`source.zip`） | 是 | 上传完成后才删除；未完成解压时**绝不删** |
| 解压临时目录（`*.extract/`） | 是 | 解压完成后清理 |
| 最终 `.src` 暂存文件 | 是 | **同盘 `renameSync` 从解压目录搬入**，不复制 |
| 解压过程中的临时文件 | 是 | 计入 `batchDirBytes()` 实测值 |
| 失败后遗留的临时文件 | 是 | `catch` 里 `rmSync(target, recursive)`；保留 ZIP 供重试 |
| 其他批次 / 用户数据 | 否 | 清理范围仅限该 `batchId` 目录 |

### 2.3 实现要点

- `BatchBudget` 增加 `workspaceBytes`，默认 `ZIP_MAX_BYTES + BATCH_STAGING_BYTES = 1536 MiB`；构造函数拒绝 `workspaceBytes < zipBytes + batchBytes` 的配置。
- `extractCeiling(zipSize) = min(batchBytes, workspaceBytes - zipSize)`：ZIP 越大，解压树可用的空间越小，两者之和始终 ≤ `workspaceBytes`。解压 worker 同时收到 `maxTotalBytes: ceiling`、`maxEntryBytes: fileBytes`、`maxEntries: BATCH_ITEM_LIMIT * 4`。
- `batchDirBytes()` 在**解压完成、ZIP 仍在盘上的那一刻**实测整个批次目录（含子目录）字节数，写入 `zip.peakBytes` 取历史最大值；若 `peak > workspaceBytes` 直接抛错，而不是事后统计。
- `importZip()` 成功路径：逐个 `renameSync`（同目录树、同文件系统，元数据操作，无副本）；仅当 rename 被特殊挂载拒绝时才 `copyThenUnlink` 回退。全部条目安全就位后才 `rmSync(zipPath)` 并置 `extracted`。
- 失败路径：删掉解压树，但**保留已校验的 ZIP**，重启后 `resume()` 看到 `state === 'ready'` 且文件存在就直接重试解压，不要求用户再选一次文件。

### 2.4 最坏情况（逐阶段，不是只报声明大小）

| 阶段 | 盘上内容 | 峰值 |
| --- | --- | --- |
| 上传完成 | `source.zip` | ≤ 512 MiB |
| 解压完成（实测点） | `source.zip` + 完整解压树 | ≤ `512 MiB + extractCeiling ≤ 1536 MiB` |
| 搬入暂存（正常 rename） | `source.zip` + 解压树（条目被逐个移走） | 单调下降 |
| 全部就位、删 ZIP 后 | `.src` 暂存文件 | ≤ 1 GiB |

`tests/import-batch-zip-peak.test.ts` 用注入的小预算逐阶段断言盘上字节数，并明确验证 **"never lets a third copy exist"**。

### 2.5 预算口径判定（任务书 2.2 第 3 条）

| 上限 | v1.1 | v1.2 | 变化 |
| --- | --- | --- | --- |
| 单文件 | 100 MiB | 100 MiB | 无 |
| 单批条目 | 100 | 100 | 无 |
| 单批 staging | 1 GiB | 1 GiB | 无 |
| 并发 | 2 | 2 | 无 |
| ZIP | 512 MiB | 512 MiB | 无 |
| 真实工作集 | 隐含、无上限（潜在 ~2.5 GiB） | **显式封顶 1536 MiB** | 收紧 |

**判定：未改变产品预算。** 没有新增或提高任何已发布常量；`workspaceBytes` 是把两个既有常量相加、对原本隐含的共存占用做硬封顶，并用 rename 消除第三份副本。实际峰值从"可能 2.5 GiB 且无人拦截"变成"≤1.5 GiB 且写入前拒绝"。按任务书第 11 节，若审核方认为"显式声明 1.5 GiB 工作集"本身属于预算变更，请退回本轮而不是直接放行；本轮**没有**请求、也没有引入更高的预算。

### 2.6 验收逐条（任务书 2.3）

| 验收项 | 判定 | 用例 |
| --- | --- | --- |
| ZIP 原件与解压文件同时存在 | ✅ | `reports each stage and never lets a third copy exist` |
| 解压后文件转移 | ✅ | 同上（rename 后 `.src` 长度逐条复核） |
| 中途失败 | ✅ | `keeps the archive (and no partial tree) when extraction is refused` |
| 重启恢复 | ✅ | `can retry the extraction from the stored archive after a restart` |
| 磁盘空间不足 | ✅ | `refuses a workspace smaller than its own parts`、`does not leave a partial tree behind when the archive is invalid` |
| 清理临时文件 | ✅ | 上述失败用例断言解压目录被清空、ZIP 保留 |

### 2.7 已知边界（如实披露）

同盘 rename 是主路径，不产生副本。只有当文件系统拒绝 rename 时才走 `copyThenUnlink` 回退：此时**单个条目**（≤100 MiB）会瞬时多一份且源随即删除；`peakBytes` 的实测点在解压完成时（rename 之前），因此这一瞬时字节不计入该读数。测试覆盖的是正常同盘路径并断言不存在第三份完整副本。若需把回退路径也纳入严格封顶，可在后续阶段移除该回退或对其单独做峰值校验——**本轮未做，也未因此提高预算**。

## 本轮修掉的真实缺陷

| 缺陷 | 表现 | 修法 |
| --- | --- | --- |
| 前端错误 `claimedSha256` 锁死批次 | 用户重选后声明摘要仍与服务端不符，`zipFinish()` 反复拒绝 | reject 时清除错误 claim，保留 `needs_reselect`，让服务端自己的哈希决定 |
| ZIP 条目摘要未透传 | `addItems()` 丢弃 `sourceSha256/sourceName`，解压产物没有内容身份 | 修正 `RawInput` 与 `addItems()`，解压条目带 `entry.sha256` |
| ZIP 面板在 jsdom 无法启动 Worker | 端到端测试挂起 | 面板测试改为验证同 batchId 重传与服务端 `sha256`；真实解压峰值交给 Node 环境的 `import-batch-zip-peak.test.ts` |
| 空 ZIP 批次标题丢失 | 上传中断、条目为 0 时历史里显示"导入 等 0 本" | `batchSummary()` 用 `batch.zip?.name` 命名 |
| 3 个既有断言因新增字段失败 | `DEFAULT_BATCH_BUDGET` 多 `workspaceBytes`、`resume()` 多 `archives` | 把断言升级为显式校验新字段（含"工作集恰等于两份之和"、普通批次 `archives: 0`），而非放宽或删除 |
