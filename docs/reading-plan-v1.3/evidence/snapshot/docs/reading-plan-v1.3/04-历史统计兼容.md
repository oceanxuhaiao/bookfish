# 04 · 历史统计口径兼容（P2-8）

对应任务书：⑧ 历史统计下界——区分"完整累计"与"可确认下界"。

---

## 1. 问题

阅读计划的历史归档有保留窗口（`archiveLimit`）。旧版本（v1.1 之前）**没有**累计计数器，v1.2 才加上 `stats`。于是存在两种完全不同的计划：

| 计划来源 | `stats` | 真实历史 |
| --- | --- | --- |
| v1.2+ 新建 / v1.2 计划 | 从诞生起逐次累加 | **完整** |
| 更早版本迁移来的计划 | 迁移时按当时仍在归档里的行**回填** | 只覆盖保留窗口内的部分，**更早的已被裁掉且不可恢复** |

v1.2 的界面把两者一律显示为"累计读完 N 本"，对后者是把下界当成了总数——这是一个会误导用户的统计口径错误。

## 2. 方案：持久化标记 + 三态推导

### 字段（`src/reading-plan.ts:91-97`）

```ts
/**
 * Whether the lifetime counters describe the COMPLETE history. A plan created
 * by this version is complete; a plan migrated from an older version (whose
 * archive window already lost rows) is not — its `stats` are a verifiable
 * LOWER BOUND, not the whole total. Absent on disk means "legacy, backfilled".
 */
statsComplete?: boolean;
```

### 三态推导（`src/reading-plan.ts:216-235`）

```ts
const statsProvided = (value as { stats?: unknown }).stats !== undefined;
const marker = (value as { statsComplete?: unknown }).statsComplete;
const statsComplete = marker === undefined ? statsProvided : marker === true;
```

| 磁盘上的形态 | 推导 | 依据 |
| --- | --- | --- |
| 有标记 `true` | 完整 | 本版本新建或已确认 |
| 有标记 `false` | 下界 | 迁移而来 |
| 无标记 + 有 `stats` | 完整 | v1.2 计划，计数从诞生起就在（`statsProvided === true`） |
| 无标记 + 无 `stats` | 下界 | v1.1 及更早，回填值只能算下界（`statsProvided === false`） |

### 写入点

| 位置 | 值 | 说明 |
| --- | --- | --- |
| `emptyPlan()`（`:140`） | `true` | 新建计划从零开始计数，是完整历史 |
| `migrateLegacyQueue()`（`:475`） | `false` | 旧队列迁移；**保守起见即使队列为空也标 false**（"至少读过 0 本"永远成立） |
| 其它任何路径 | 不写 | 已有值原样保留；`validatePlan` 只做推导与回填，不改写已有标记 |

**截断不改变标记。** 归档被裁（`truncatedCount > 0`）只影响"能列出多少条"，不影响累计计数——累计计数在条目被裁掉时已经加过了。所以 `statsComplete` 与 `archiveKept` / `truncatedCount` 相互独立，测试有专门断言（`tests/plan-stats-complete.test.ts` 第 6 例）。

## 3. 视图与界面

### 视图（`src/library.ts:874`）

```ts
statsComplete: plan.statsComplete === true,
```

`planView()` 把计划内部的 `boolean | undefined` 收敛成确定的布尔值交给 UI，避免前端再做三态判断。

### 文案（`src/webui/plan.ts:71-89`）

```ts
const complete = plan.statsComplete !== false;
summary.textContent = say(
  `计划 ${plan.total} 本 · ` + (complete ? `累计读完 ${plan.completedCount} 本` : `至少累计读完 ${plan.completedCount} 本`) + ...,
  `${plan.total} planned · ` + (complete ? `${plan.completedCount} finished in total` : `at least ${plan.completedCount} finished in total`) + ...);
```

下界计划追加说明（`plan-history` 注释）：

> 此计划由旧版本迁移而来，更早的完读历史可能已超出保留窗口，以上累计数字是可确认的下界，不是完整总数。

## 4. 数据兼容

| 问题 | 结论 |
| --- | --- |
| 旧计划读进来会怎样？ | `validatePlan` 按上表三态推导，旧计划得到 `statsComplete = false`，行为正确，无需迁移脚本 |
| 新写的计划旧版本能读吗？ | 能。`statsComplete` 是**可选**字段，旧版本校验器忽略未知字段，读到的仍是合法计划 |
| 需要数据迁移吗？ | **不需要**。没有重写已有计划文件；标记在下次正常保存时自然写入 |
| 会改变现有计数吗？ | 不会。只增加"这个数是否完整"的标记，不改任何累计值 |

## 5. 字段命名（本轮修正）

该标记最初命名为 `historyComplete`。全量回归时 `tests/predeploy-data-lifecycle.test.ts` 失败：

```
AssertionError: expected '{"format":"bookfish-backup-v1",...' not to match /story/i
```

原因是 `hi` + `story` + `Complete` 恰好包含子串 `story`，撞上了 predeploy 降级安全守卫——该守卫要求**JSON 备份里不得出现故事数据**（故事数据在独立 sidecar），用 `/story/i` 做启发式检查。

处置：**字段改名 `statsComplete`**（语义不变：统计是否完整），**守卫一字未改**。理由：守卫的粗粒度检查是有意为之的"宁可误报"，为它开口子等于削弱降级安全；而改名没有任何代价——该字段本轮才引入、尚未发布，不存在兼容包袱。

## 6. 验收（`tests/plan-stats-complete.test.ts` 6 例 + 视图/UI 断言）

| 用例 | 断言 |
| --- | --- |
| 新计划 | `statsComplete === true`，落盘再读仍为 `true` |
| 无 `stats` 的旧计划 | 回填后 `false` |
| v1.2 计划（有 `stats`、无标记） | 推导为 `true` |
| 显式 `false` | 保留 `false`（不被推导覆盖） |
| `migrateLegacyQueue` | 结果 `false`，含空队列 |
| 归档截断 | 截断不改变 `statsComplete` |

配套：`tests/plan-display.test.ts` 断言 `planView().statsComplete`；`tests/webui/plan-panel.test.ts` 断言"累计读完 N 本"与"至少累计读完 N 本"两个分支、以及下界说明文案出现（用 `· 累计读完` 前缀区分，避免子串误匹配）。
