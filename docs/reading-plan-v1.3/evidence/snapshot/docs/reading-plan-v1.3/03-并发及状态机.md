# 03 · 并发保护、状态机与无内容终态（P1-5 / P2-7）

对应任务书：⑤ ZIP 解压并发保护；⑦ 空 ZIP / 隐藏文件 / 纯不支持 / 纯目录的明确终态。

---

## 1. 同批次解压 single-flight（P1-5）

### 为什么要做

解压有三个入口能同时到达：前端 `zipFinish`、`resume()` 的恢复扫描、用户手动重试。v1.2 没有互斥，两次解压会往同一批次目录写两套文件、重复 `addItems`、互相覆盖 `.src`，峰值也翻倍。

### 实现（`src/import-batches.ts:401-410`）

```ts
private readonly extracting = new Map<string, Promise<ZipExtractResult>>();  // :146

async importZip(batchId, zipPath, signal): Promise<ZipExtractResult> {
  const flight = this.extracting.get(batchId);
  if (flight) return flight;                       // 已在飞：直接加入，不新建
  const run = this.extractArchive(batchId, zipPath, signal);
  // 在首个 await 之前同步登记：并发调用者即使恰好落在检查与启动之间也能看到
  this.extracting.set(batchId, run);
  try { return await run; }
  finally { this.extracting.delete(batchId); }
}
```

关键点：`this.extracting.set()` 在 `await` **之前**同步执行。JavaScript 单线程下，任何并发调用者要么看到已登记的 flight（加入），要么在登记之前根本进不来——不存在"两个调用都通过 `get` 检查后各自启动"的窗口。

### 状态机（`extractArchive`，`src/import-batches.ts:412-424`）

```
                 zipBegin                 zipFinish(长度+摘要通过)
   (none) ──────────────▶ uploading ──────────────────────────▶ ready
                              │                                  │
                              │ 长度/摘要不符（refuse）           │ extractArchive
                              ▼                                  ▼
                        needs_reselect ◀── 恢复失败/rename 失败 ── extracted（终态）
                              │
                              │ zipReselect（需有可信摘要）
                              ▼
                          uploading
```

| 状态 | 进入解压？ | 依据 |
| --- | --- | --- |
| `uploading` | 否：`The archive has not been verified yet; finish the upload first` | `:421` |
| `needs_reselect` | 否：`zipFinish` 直接拒绝（`:619`），必须先重选 | `:619` |
| `ready` | 是（含"上次解压失败后的重试"，字节已验证仍在盘上） | `:421` |
| `extracted` | 否：返回 `alreadyExtracted: true`，空结果 | `:420` |

`extracted` 是**单向终态**：没有任何路径能把它改回 `uploading`/`ready`。`zipReselect` 对 `extracted` 明确抛 `This archive has already been extracted`（`:667`）。

### 恢复受控调度（`resume()`，`:714-751`）

```ts
let chain: Promise<unknown> = Promise.resolve();
for (const batch of this.library.importBatches()) {
  if (batch.zip?.state !== 'ready') continue;
  if (!existsSync(this.zipPath(batch.id))) continue;
  const id = batch.id, path = this.zipPath(batch.id);
  chain = chain.then(() => this.importZip(id, path)).then(
    () => undefined,
    () => { this.library.updateImportBatch(id, (draft) => { if (draft.zip) draft.zip.state = 'needs_reselect'; }); },
  );
  archives += 1;
}
```

串行链：后一个只在前一个 settle 之后才开始。单个失败被就地吞下并置 `needs_reselect`，不阻断后续批次。**默认一次一个**，重启时多个中断批次不会叠加峰值。

另外 `resume()` 对 `uploading` 的处理保持 v1.2 语义：半截上传无法跨进程续传，删半截文件、置 `needs_reselect`，给出明确重选入口（`:723-727`）。

### 验收（`tests/import-batch-zip-concurrency.test.ts`，4 例）

| 用例 | 断言 |
| --- | --- |
| `Promise.all` 两次 `zipFinish` | 两次都成功；`expect(second).toBe(first)`——**同一个结果对象引用**（证明是加入而非重跑）；`.src` 恰好 3 份；ZIP 已删除 |
| 完成后再 finish | `alreadyExtracted === true`，`added` 为空，条目数不变 |
| 上传未完成 / 已开始解压 | 未传完时 `finish` 被拒（`incomplete`）；解压后 `zipChunk` 抛 `not accepting data`，`zipReselect` 抛错 |
| 多批次 resume | 3 个 ready 批次全部 `extracted`；`vi.spyOn` 包裹 `importZip` 统计并发，**峰值恒为 1** |

> 说明：第 3 例的"未传完"在上一轮全量回归中曾失败——原因是 fixture ZIP 压缩后仅 523 字节，一个 8 KiB 分片就等于整个文件，测试前提不成立（源码行为正确）。已把测试改为严格前缀上传，**未放宽任何源码限制**，详见 `05`。

## 2. 无内容归档的明确终态（P2-7）

### 问题

v1.2 把"空归档 / 只有隐藏文件 / 只有目录 / 全是不支持格式"当成 `addItems([])` 处理，而 `normalizeInputs` 拒绝空数组——于是解压成功却抛 "Select at least one file"，批次停在非终态，重启后 `resume()` 又看到 `ready`（或半截状态）**反复重新解压**，永远好不了。

### 实现

**（a）空条目列表不再走 `addItems`**（`src/import-batches.ts:462-465`）：

```ts
const result = entries.length
  ? this.addItems(batchId, entries.map(...))
  : emptyAddResult();      // 解压成功，只是没有可导入的东西
```

`emptyAddResult()` 返回 `{ added: [], duplicates: [], unsupported: [], tooLarge: [], overBudget: [], overflow: 0 }`（`:131-133`）。

**（b）终态收口**（`:490-510`）：

```ts
if (items.length === 0) {
  rmSync(zipPath, { force: true });
  this.library.updateImportBatch(batchId, (draft) => {
    if (draft.zip) draft.zip.state = 'extracted';
    draft.status = 'completed';
  });
  return result;
}
if (items.every((item) => item.staged || item.status === 'completed' || !item.supported)) {
  rmSync(zipPath, { force: true });
  this.library.updateImportBatch(batchId, (draft) => { if (draft.zip) draft.zip.state = 'extracted'; });
}
```

- `state = 'extracted'`：**重启不再解压**（`extractArchive` 首行就返回 `alreadyExtracted`，`resume()` 也只扫 `ready`）。
- `status = 'completed'`：批次在界面上是"已完成"，不是"卡住"。
- 删除 ZIP：不留 512 MiB 垃圾。
- **不自动入计划**：`addItems` 没被调用 → 没有条目 → `applyToPlan` 无事可做；`applyToPlan` 本身也是显式用户动作，不自动触发。

### 数据兼容

**没有新增状态值。** `BatchZip.state` 仍是原来的四态（`uploading | needs_reselect | ready | extracted`），`batch.status` 沿用既有 `preview | running | completed`。因此：

- 旧数据（v1.2 写入的批次记录）无需迁移，反序列化不受影响；
- 新版写入的终态在旧版读取时也是合法值（旧版不认识"空归档"这个业务含义，但状态本身可读，最坏表现是旧版把它当作一个 0 条目的已解压批次）；
- 端到端数据格式**没有变更**，不构成"新持久化架构"。

### 界面

`src/webui/batch-import.ts:311-314`（双语 `say(zh, en)`）：

> 解压完成，但未发现可导入的书籍（可能是空压缩包、只有隐藏文件或全部是不支持的格式）。此批次不会自动加入阅读计划，可以清理这条记录。

### 验收（`tests/import-batch-zip-terminal.test.ts`，5 例）

| 用例 | 断言 |
| --- | --- |
| 空 ZIP | `state = extracted`、`status = completed`、0 条目、ZIP 已删、重启 `report.archives === 0` |
