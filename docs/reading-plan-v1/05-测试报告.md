## 3. 关键行为是怎么被证明的

**"重排不动正文"**（`reading-plan-library`）——不是断言代码没写，而是前后对比可观测字段：

```
before: revision / totalChars / confirmedChars / confirmedSegments / journal 条数 / reviews 版本数 / selected
after : 同上，全部相等；只有 plan.items 顺序变化
```

**"当前书不可被抢占"**（`library` + `plan-panel`）——三处独立证据：
1. `removeFromPlan(activeItem, {status:'removed'})` 抛 `locked`；
2. `place('top')` 对一个在后面排队的书，落点被夹到 `activeIndex + 1`（面板断言顺序仍是 `甲, 丙, 乙`）；
3. 面板里当前书那一行**一个按钮都没有**，停止阅读的按钮在"正在读"卡片上。

**"跳过不是完读"**——同时断言 `planView().completedCount === 0`、archive 的 `status === 'skipped'`、书的 `confirmedChars` 不变、书还在书架。

**"重启不丢计划"**——关库重开，断言 `items` 的 `bookKey` 顺序与 `item.id` 都与重启前一致，且 `revision` 未变（没有无谓写入）。

**"批量导入用的是同一个解析器"**——端到端用例真的起了 worker 线程、真的写了 paged blob、真的让书进了书架；坏文件（含 `\u0000` 控制字符）得到的是既有的 `Binary or control characters are not supported` 错误文本，证明走的不是新代码路径。

**"中断恢复"**——两例：
- 暂存字节完好 → `resume()` 返回 `{resumed:1, reselect:0}`，条目回到 `pending` 并最终 `completed`；
- 暂存字节被删 → 返回 `{resumed:0, reselect:1}`，条目变 `needs_reselect` 且提示"请重新选择"。

**"并发有限"**——纯函数层面直接断言 `dispatchable(batch, 0).length === 2`、`dispatchable(batch, 2).length === 0`、`dispatchable(batch, 1).length === 1`；端到端层面观察 3 本同时导入全部完成。

## 4. 回归中被修掉的真实缺陷（写在这里便于审核）

| 缺陷 | 表现 | 修法 |
| --- | --- | --- |
| 迟到进度回调把已完成条目打回 `validating` | 批次永远停在 `running`（`import-batch-run` 的坏文件用例 20s 超时） | `setItemStatus` 拒绝终态回退；`watch()` 落盘前二次校验条目状态并清 timer |
| 失败分支绕过状态机 | 同上，批次不收敛（probe 脚本显示两本都已终态，批次仍 `running`） | `settle()` 的失败分支改走 `setItemStatus('failed')`，让 `settleBatch()` 正常收敛 |
| `settle()` 无条件删除暂存字节 | 被取消的条目无法重试（只能重新选文件） | 只有 `done` 才回收暂存文件 |
| `editPlanSeries` 在 updater 内读 `planView()` | 返回的是**变更前**的视图（`create` 后拿不到新系列） | 先把变更写进 draft，再在 `change()` 外用 `planView()` 取视图 |
| 普通重排可以把书插到当前书前面 | 违反"当前书锁定" | `waitingTarget()` 在库层夹紧落点；当前书条目本身禁止移动；整组含当前书则拒绝 |
