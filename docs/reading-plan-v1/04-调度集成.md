# 04 · 调度集成

## 1. WP0 现状盘点（动工前）

| 项 | 事实 |
| --- | --- |
| 基线 | `dd4f0b9` = `origin/main` v0.66.7，101 个测试文件，`1113 passed \| 1 skipped (1114)` 全绿 |
| `LibraryState` | `schema: 3`；文件快照 `schema: 6`（有连载时 7） |
| 跨书队列 | `selection.queue: ReadingQueueItem[]`（`queued\|active\|done\|cancelled`，上限 50） |
| 自动切书 | `SelectionCoordinator.autoAdvance()`，被 `ReadingScheduler` 在 `hooks.autoAdvance` 里调用 |
| 调用时机 | `scheduler.tick()` 内：`(!current \|\| current.complete) && !goal.reached && phase==='idle' && now-idleSince>=30000 && !active && !cognitionRunning && restUntil<=now` 才调用 |
| `bookfish_plan_reading` | **本版本不存在同名工具**；对应能力是 `bookfish_acquire(action="plan", planAction="queue"\|"defer")` |
| 自主选书门禁 | `self_selected_unfinished` / `round_paused` / `round_exhausted` / `cooldown` / `already_in_library` / `duplicate_work` / `externalPolicyRevokedAt`（持久撤销栅栏） |
| 完读判定 | 本地书 `frontier === segments.length`；远程/连载需缓存完整 + `publicationStatus === 'finished'`；连载 readiness `backlog\|waiting_content\|caught_up\|finished\|conflict` |
| 进度写入 | 只有 `readNext` / `finish` / `finishMany`（`library.ts`） |

结论：跨书队列早已存在，只是长在 `selection` 里；把它升级成"统一计划"，同时保持"进度只有一条写入路径"是这次改动的核心约束。

## 2. 没有第二套调度器

```
ReadingScheduler ──(idle 30s, 无 active/cognition, 未达日章目标, 非 rest/routine)──▶ hooks.autoAdvance
                                                                                        │
                                                                       SelectionCoordinator.autoAdvance()   ← 现在是薄委托
                                                                                        │
                                                                       Library.advancePlan(scheduler.status())
                                                                                        │
                                                                              PlanCoordinator.attempt()
                                                                                        │
                                                                     Library.selectPlanned(bookKey)   ← 只切"读哪本"
```

`PlanCoordinator` 的能力边界（`src/plan-coordinator.ts` 全文只有 ~70 行）：

- ✅ 读 `library.status()` / `library.plan()` / `library.list()`；
- ✅ 调 `selectPlanned()`（切 selected + 记 `startedAt`，一次 `change()`）；
- ❌ 不读正文、不建 task、不写 frontier、不确认、不写手账/读后感/故事记忆。

因此"自动切书"永远不会顺手把上一本标成读完，也不会替下一本预读。

## 3. 交接门禁（8 条，逐条对应代码）

`PlanCoordinator.attempt()` 的判定顺序与返回原因：

| 顺序 | 返回 `reason` | 条件 |
| --- | --- | --- |
| 1 | `not_mounted` | `!status.mounted` |
| 2 | `paused` | `status.paused` |
| 3 | `current_incomplete` | 有当前书但 `!complete` |
| 4 | `pending_text` | `status.pending`（有已发出未确认的正文） |
| 5 | `review_pending` | 当前书 `complete` 但存在 `pending` review job |
| 6 | `routine` | `scheduler.routine`（睡眠/用餐） |
| 7 | `resting` | `scheduler.restUntil > now` |
| 8 | `plan_disabled` | `plan.enabled === false` |
| 9 | `deferred` | 队首条目 `notBefore > now`（**不越位**，直接停） |
| 10 | `plan_exhausted` / `plan_empty` | 没有可读条目 / 计划为空 |

第 8 条之外的"全局自主阅读开关""聊天优先"由 `scheduler` 决定是否调用 `autoAdvance`，`PlanCoordinator` 不重复判定——单一职责，避免两处门禁打架。

**完读门槛没有降低**：本阶段零改动 `complete` 计算、`readiness` 分支、`hasPendingReviewJob` 语义。`caught_up`（连载追平）、`waiting_content`、网络失败、导入完成、入队都不产生 `complete`。

## 4. 与既有自选书门禁的接缝

| 旧行为 | 新行为 |
| --- | --- |
| `fulfill()` 追加 `selection.queue` | `addToPlanAtomic([key], {source:'persona', intentId}, updater)`，一次快照同时写 intent 回执与计划条目 |
| `plan(intentId,'defer',t)` 改 queue 行 `notBefore` | 在计划里：已在计划则 `setItemNotBefore`，否则 `addToPlan({notBefore})` |
| `abandon` / `cancel` 把 queue 行标 `cancelled` | `removeFromPlan(item.id, {status:'removed', keepReading:true, reason})` —— **不删书、不清进度** |
| `reconcileQueue()` 重建 queue | 对 `queueOnImport` 且非终态的 intent 幂等补条目（已存在则只保留 notBefore） |
| `onSelectionChanged()` 标 active | 只 `refresh()`；active 由 `selected` 派生 |

`self_selected_unfinished` 这类承诺门禁仍然有效：它读的是 intent 状态，与计划无关，所以"排队/暂停/临时切书/重启"依旧解不开承诺。

## 5. 为什么没有新增常驻模型工具（Token 优化策略未变）

任务书要求不得修改 Token 优化策略。实测：

```
src/ENV_PROMPT.md            680 chars
BOOKFISH_TOOL_DECLS JSON   13294 chars   （16 个声明）
合计                       13974 chars
预算：tools ≤ 13400，prompt+tools ≤ 15000，prompt ∈ [300, 800]
```

我先按常规做法加了一个 `bookfish_plan` 工具（schema 1172 chars），实测 `tools` 变成 **14465 > 13400**，直接击穿既有预算守卫。于是改为**不新增常驻工具**：

- 模型侧：`bookfish_get_status.plan` 给紧凑投影（`enabled/revision/total/completed/current/next/seriesCount/deferred/missing`），足以知道"在读哪本、下一本是谁、有没有暂缓/缺书"。
- 排队能力：继续用既有的 `bookfish_acquire(action="plan")`。
- 计划编辑：**属于用户决定**，只在 WebUI 提供（`plan_update` / `plan_add` / `plan_series` / `plan_suggest`）。这也更符合产品语义——宠物不该自己给用户的歌单排序。
- 知识：新增协议段落进 `src/protocol/reading.md`（按需 `bookfish_help("reading")` 加载，常驻 0 成本）。

结果：`tools.length` 与 `prompt.length` 与改造前**完全一致**，`tests/context-budget.test.ts` 12 项全绿。

## 6. 自动切书的可观察后果

| 场景 | 结果 |
| --- | --- |
| 读完第一本，计划里还有第二本 | 下一个 idle 机会切到第二本；第一本仍在书架、进度 100%、可回头写读后感 |
| 第一本的读后感 job 还 pending | 不切（`review_pending`）；job 终态失败后放行 |
| 第二本被用户"暂时跳过" | 直接读第三本；跳过的书进度不变 |
| 计划头部条目被暂缓 | 停在 `deferred`，不越到后面的书（尊重用户排的"这周先别读"） |
| 计划里下一本已从书架删除 | 跳过它继续找；打开库时它已被 `reconcilePlan` 移入归档 |
| 连载追平（`caught_up`） | 不切，仍停在原书（不算完读） |
| 全局自主阅读关闭 / 睡眠 / 用餐 / 休息中 | 不切（由 scheduler 与 coordinator 双重拦住） |
| 重复回调/重复 tick | `selectPlanned` 幂等（`startedAt` 只写一次）；第二次 tick 因当前书未读完直接 `current_incomplete`，不会连环跳书 |
