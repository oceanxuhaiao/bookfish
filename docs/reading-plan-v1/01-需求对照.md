## 阶段三 · 调度集成

| # | 任务书要求 | 结论 |
| --- | --- | --- |
| 3.0 | 先盘点既有 `ReadingScheduler` / `ReadingQueueItem` / 自主选书状态 / `bookfish_plan_reading` / `read_next` / `finish_reading` / 自动切书门禁 | 见 `04-调度集成.md`「现状盘点」。本版本 `bookfish_plan_reading` 实际对应 `bookfish_acquire(action="plan")`；`ReadingQueueItem` 是 `selection.queue` 的 50 条上限队列 |
| 3.1 | 禁止开发第二套能直接推进进度的调度器 | `PlanCoordinator` 只调用 `library.selectPlanned()`；进度只由 `readNext` / `finish` / `finishMany` 推进（`src/library.ts` 未新增任何 frontier 写入路径） |
| 3.2 | 自动切书必须同时满足 8 条门禁 | `attempt()` 逐条返回 `not_mounted / paused / current_incomplete / pending_text / review_pending / routine / resting / plan_disabled / deferred / plan_exhausted / plan_empty` |

8 条门禁的代码与测试：

| # | 门禁 | 代码 | 测试 |
| --- | --- | --- | --- |
| 1 | 真实完读 | `status.current.complete`（frontier === segments.length；连载需 `publicationStatus==='finished'` 且缓存完整） | 「refuses while the current book still has unread text」「does not treat the last chapter as finished…」 |
| 2 | 无未完成正文任务 | `status.pending` | 「refuses while a passage is offered but not yet confirmed」 |
| 3 | 无未结束认知任务 | 交给既有 `scheduler` 的 idle / `cognitionRunning` 判定；coordinator 不重复实现 | 既有 `tests/scheduler.test.ts`、`tests/batch-reading.test.ts` 全绿 |
| 4 | 进度已保存 | 交接通过 `selectPlanned()` 单次 `change()` 完成"切书 + 打 startedAt"，不产生中间态 | 「hands off to the next planned book and stamps its start in one snapshot」 |
| 5 | 完读感想成功或终态失败 | `hasPendingReviewJob()` | 「waits for the finished book review, then allows a terminal failure」 |
| 6 | 无用户锁定/暂停 | `status.paused` + `scheduler.routine` + `restUntil` | 「respects pause, routine, rest and the plan switch」 |
| 7 | 下一本已入架且身份明确 | `views.get(item.bookKey)`（以 `bookKey` 为准，缺书跳过不猜） | 「honours a deferral and skips an entry whose revision is gone」 |
| 8 | 全局自主阅读/作息/聊天优先允许 | 由既有 scheduler 决定何时调用 `hooks.autoAdvance`；coordinator 只在被调用时才动作 | 既有 `tests/scheduler.test.ts`；本阶段 `selection.autoAdvance()` 改为薄委托 |

| # | 任务书补充 | 结论 |
| --- | --- | --- |
| 3.3 | 完读门槛不得降低（网络失败、缓存末尾、连载追平、导入完成、入队都不算完读） | 未改动任何 `complete` 判定；`caught_up` / `waiting_content` / `conflict` 仍走既有 readiness 分支 |

## 数据结构与持久化

| # | 要求 | 结论 |
| --- | --- | --- |
| 5.1 | `ReadingPlan` / `ReadingPlanItem` / `Series` / `ImportBatch` | `src/reading-plan.ts`（`ReadingPlan` / `PlanItem` / `PlanSeries`）、`src/import-batch.ts`（`ImportBatch` / `BatchItem`） |
| 5.2 | 必须使用现有持久化架构（library.json 原子快照 + history.sqlite） | 两者都是 `LibraryState` 的字段，写入口只有 `Library.change()` → `atomicWrite`（`openSync('wx')` + `fsyncSync` + `renameSync`）；tasks/episodes 仍走 `history.sqlite` |
| 5.3 | 不得自建 WAL / GC / 分段存储 | 未新增任何存储子系统；批次暂存复用既有 `transfers/` 目录与 `ImportJob` 的 `<uuid>.import` 暂存 |
| 5.4 | 幂等 | `addToPlan`（重复即 `duplicates`）、`addBatchItems`（同路径去重）、`stage()`（连续偏移）、`applyToPlan`（重复加计划无副作用）、`retryItem` |
| 5.5 | 重启恢复 | `syncPlan`（计划迁移/对账/已完工归档）+ `ImportBatches.resume()`（in-flight 项回到 pending 或 `needs_reselect`） |
| 5.6 | 旧数据兼容迁移 | `migrateLegacyQueue()` + `validatePlan(undefined)` / `validateBatches(undefined)` 返回空结构 |
| 5.7 | 备份回滚 | 沿用既有 `export` / `restore` / `writeArchive` / `restoreArchive`；计划与批次在备份里 |
| 5.8 | 不静默丢字段 | `validatePlan` / `validateBatches` 对篡改**抛错**而不是修补；`library.json` 写失败即整体不提交 |
| 5.9 | 迁移失败不覆盖原数据 | `syncPlan` 与 `change()` 同一快照；任何异常都会让 `atomicWrite` 不执行（见 `06-数据安全与回滚.md`） |
